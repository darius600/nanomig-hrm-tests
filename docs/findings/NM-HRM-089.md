## Source requirement

**Printed p. 22** gives the rule every WAIT follows:

> The WAIT instruction causes the Copper to wait until the video beam counters are equal to (or greater than) the coordinates specified in the instruction. While waiting, the Copper is off the bus and not using memory cycles.

**Printed p. 23** explains why `$FFFF,$FFFE` stops the Copper, and names the largest position that does occur:

> The following example WAIT instruction waits for scan line 255 and horizontal position 254. This event will never occur, so the Copper stops until the next vertical blanking interval begins.

> To understand why position VP=$FF HP=$FE will never occur, you must look at the comparison operation of the Copper and the size restrictions of the position information. Line number 255 is a valid line to wait for, in fact it is the maximum value that will fit into this field. Since 255 is the maximum number, the next line will wrap to zero (line 256 will appear as a zero in the comparison.) The line number will never be greater than $FF. The horizontal position has a maximum value of $E2. This means that the largest number that will ever appear in the comparison is $FFE2. When waiting for $FFFE, the line $FF will be reached, but the horizontal position $FE will never happen. Thus, the position will never reach $FFFE.

and, under *Horizontal Beam Position*:

> The horizontal beam position has a value of $0 to $E2. The least significant bit is not used in the comparison, so there are 113 positions available for Copper operations.

> In PAL, they are all 227 long.

**Printed pp. 32 and 33**, in *A Copper Loop Example*, use $E2 as the position that finishes a line:

> To make sure that the Copper does not loop back before the vertical position has changed and cause another interrupt on the same scan line, wait for the horizontal position to be $E2 after each interrupt. Position $E2 is horizontal position 113 for the Copper and the last real horizontal position available. This will force the Copper to the next line before the next WAIT.

and the listing on p. 33 does it with the vertical position masked:

> DC.W    $00E3,$80FE   ; Wait for Horizontal $E2
> ; This is so the line gets finished before
> ; we check if we are there  (The wait above)

**Printed p. 30** draws the line between the two kinds of position:

> A typical instruction is to WAIT for VP = $FF and HP = $FE. An HP of greater than $E2 is not possible.

**Printed p. 219** places the start of vertical blanking, the end of the interval p. 23's stop lasts for:

> Bit 5, VERTB, causes an interrupt at line 0 (start of vertical blank) of the video display frame.

**What the pages require of a WAIT for ($FF,$E2).** A WAIT for ($FF,$E2) fetched on line 255 ends on line 255, when the horizontal count reaches $E2, because $FFE2 *"will ever appear in the comparison"*; and it must end there or not at all, because after line 255 *"the next line will wrap to zero"*. p. 32 calls $E2 *"the last real horizontal position available"*, and p. 33's listing relies on a WAIT for it ending on the line it is fetched on. A WAIT for any position beyond $E2 on line 255 is the other case: p. 23 and p. 30 say it never ends, and the Copper stops until line 0. No page says on which colour clock the Copper notices a comparison that has become true; p. 20 adds only *"The Copper is a two-cycle processor that requests the bus only during odd-numbered memory cycles"*.

## RTL and measurement

**The comparison is evaluated once per colour clock and is not held.** [`src/minimig-aga/agnus_copper.v#L305-L312`](https://github.com/harbaum/NanoMig/blob/4495f86fbb0611e53649165faa36f1125e062f18/src/minimig-aga/agnus_copper.v#L305-L312), with `assign clk_ena = hpos[0];` ([`#L131`](https://github.com/harbaum/NanoMig/blob/4495f86fbb0611e53649165faa36f1125e062f18/src/minimig-aga/agnus_copper.v#L131)):

```verilog
if (clk_ena)
  if ({vpos[7:0],hpos[8:2]} >= {vercmp[7:0],horcmp[8:2]})
    beam_match <= 1'b1;
  else
    beam_match <= 1'b0;
```

The comparator sees eight bits of the line, `.vpos(vpos[7:0]),` ([`agnus.v#L419-L420`](https://github.com/harbaum/NanoMig/blob/4495f86fbb0611e53649165faa36f1125e062f18/src/minimig-aga/agnus.v#L419-L420)), so line 256 compares as 0, as p. 23 says. A line is 227 counts, 0 to $E2 (`parameter HTOTAL_VAL = 8'd227 - 8'd1;` and the end-of-line test at [`agnus_beamcounter.v#L86`](https://github.com/harbaum/NanoMig/blob/4495f86fbb0611e53649165faa36f1125e062f18/src/minimig-aga/agnus_beamcounter.v#L86) and [`#L250`](https://github.com/harbaum/NanoMig/blob/4495f86fbb0611e53649165faa36f1125e062f18/src/minimig-aga/agnus_beamcounter.v#L250)), and the line number steps at count 1 of the next line, `if (hpos==2) //actual chipset works in this way` ([`#L312-L317`](https://github.com/harbaum/NanoMig/blob/4495f86fbb0611e53649165faa36f1125e062f18/src/minimig-aga/agnus_beamcounter.v#L312-L317), [`#L331-L335`](https://github.com/harbaum/NanoMig/blob/4495f86fbb0611e53649165faa36f1125e062f18/src/minimig-aga/agnus_beamcounter.v#L331-L335)). So on line 255 the comparison for ($FF,$E2) is true for one count only, $E2 itself.

**The state machine reads it one register later, and only on enabled cycles.** `beam_match_wait <= beam_match_skip;` ([`#L314-L320`](https://github.com/harbaum/NanoMig/blob/4495f86fbb0611e53649165faa36f1125e062f18/src/minimig-aga/agnus_copper.v#L314-L320)) is what the WAIT state tests, `if (beam_match_wait) // wait is over, fetch next instruction` ([`#L487-L509`](https://github.com/harbaum/NanoMig/blob/4495f86fbb0611e53649165faa36f1125e062f18/src/minimig-aga/agnus_copper.v#L487-L509)), and the state changes only `else if (enable) // go to next state` ([`#L370-L376`](https://github.com/harbaum/NanoMig/blob/4495f86fbb0611e53649165faa36f1125e062f18/src/minimig-aga/agnus_copper.v#L370-L376)). `enable` alternates, and a forced cycle at the start of each line re-phases it, [`#L342-L360`](https://github.com/harbaum/NanoMig/blob/4495f86fbb0611e53649165faa36f1125e062f18/src/minimig-aga/agnus_copper.v#L342-L360):

```verilog
if (hpos[8:1]==8'h01) bus_blk <= 1; //cycle $E1 is blocked
else bus_blk <= 0;
...
if (bus_blk) bus_ena <= 1; //cycle $E2 is usable
else bus_ena <= ~bus_ena;
...
assign enable = ~bus_blk & bus_ena & clk_ena;
```

The comments name these cycles `$E1` and `$E2`; the condition is count 1 of the counter VHPOSR reads, and its effect lands on counts 2 and 3. The module's header comment gives the reason, *"if the horizontal line contains odd number of CCK cycles (short lines of NTSC mode and all lines of PAL mode) there is a place where two cycles usable by the copper are located back to back"* ([`#L133-L136`](https://github.com/harbaum/NanoMig/blob/4495f86fbb0611e53649165faa36f1125e062f18/src/minimig-aga/agnus_copper.v#L133-L136)).

**Read from these lines, the one-count match is never seen.** `enable` is high at the odd counts 3 to $E1 and at count 0, low at every even count from 4 to $E2 and at count 1, and low at count 2, the blocked cycle. A comparison true at count n reaches the state machine at count n+2. For $E2 that is count 1 of line 256, where `enable` is low, and by the next enabled count the comparison is false again; line 256 compares as 0, so the WAIT stays pending until the restart. On an ordinary line v the same count is missed, and the WAIT ends once line v+1's number is in the comparison: true from count 2, seen at count 4, acted on at count 5 — the same count at which a WAIT for any position beyond $E2 on line v ends. The same reading gives every offset measured below.

### Measured

Run B of [`integration/ch2-copper-beam`](../../integration/ch2-copper-beam) gives each field its own list L_j: `WAIT($FF,$40)` and the marker a_j, then `WAIT($FF,h_j)` and the marker x_j, then `$FFFF,$FFFE`; h_0 is $E2 and h_1 to h_14 are $E4 to $FE. In L_0 the WAIT is `$FFE3,$FFFE` ([`prog_b.s`](../../integration/ch2-copper-beam/prog_b.s) builds the lists). The program reads VPOSR and VHPOSR as long words without pause, and the test places every Copper fetch against that trace and against the earliest and the latest start of line 0 of the next field. Identical on fx68k and TG68K:

The form of the WAIT is in the package's [specification](../../integration/ch2-copper-beam/SPECIFICATION.md) (the notation, line 131). In `integration/ch2-copper-beam`, `P6-LARGEST` is graded at `test_ch2_copper_beam.cpp:1470-1471` and the measurement is printed at `:1458-1464`.

**The WAIT for $E2 behaves on line 255 exactly as the WAITs beyond it.** Where the package's two readings of the Copper's cycle parity put x_0 161 to 163 slots after a_0, x_0's first word is read 13102 slots after a_0 in PAL and 1752 in NTSC: 2 slots (PAL) and 1 slot (NTSC) after the latest start of line 0 of the next field, where the word after the WAIT is read for every h_j from $E4 to $FE, in all 19 PAL and all 23 NTSC fields of those lists. A read inside line 0 is outside P6's window, which ends at the earliest start of line 0 (p. 219), so `P6-NEVER`, the same measurement for $FE, is green. `PRE-B-L255` and `PRE-B-WAITED` are green: the second word of every `WAIT($FF,h_j)` is fetched on line 255, and every `WAIT($FF,$40)` before it waited. `P6-CONTROL`, `WAIT($FE,$FE)` in an extra field, is green as well: the marker after it is fetched in the same field and the `WAIT($FF,$40)` after it waited (62 slots), so the measurement sees a WAIT that ends.

**On ordinary lines the package measures the same comparison and grades it only where the pages agree.** Run C waits, on line u_k, for (u_k, $10) and then for (u_k, h_k), and records D_k, the slots between the two markers; p. 23 and p. 24 give D_k = h_k − $10. It also waits for (w_j, g_j) with g_j from $E4 to $FE and then for (w_j+1, $40), and records E_j between those two markers. Identical on fx68k and TG68K, PAL and NTSC:

```text
MEASURED: P4 PAL run C: D_k - (h_k - $10) for h_k = $D2..$E2 (reading A predicts 0 or 1, reading B -1 or 0): k=105:0 k=106:0 k=107:0 k=108:0 k=109:0 k=110:0 k=111:0 k=112:0 k=113:3
MEASURED: P4-C PAL run C: E_j and the line of r2_j per j: j=0(w=$A4, expected line 165):{E=62 line 165} j=1(w=$A6, expected line 167):{E=62 line 167} ... j=13(w=$BE, expected line 191):{E=62 line 191}
```

(the P4-C line is shortened here; all fourteen read `E=62`, and the NTSC lines read the same). Every WAIT for an even position up to $E0 ends at the same offset from its position as the WAIT for $10; the WAIT for $E2 ends 3 counts later, at $E2 + 3, which on a 227-count line is count 2 of the next line. A WAIT for $E4 to $FE ends 62 counts before a WAIT for $40 of the next line, which is also count 2 of that line (the marker delay cancels in both differences). So on an ordinary line a WAIT for $E2 ends where a WAIT for a position beyond $E2 ends. The graded lines `P4-A`, `P4-B` (D_k strictly increasing up to $E2) and `P4-C` are green on both cores; the 3 lies outside both bands the package records for the pages' two readings of the Copper's cycle parity and is measured, not graded.

## Risks and unknowns

- **All four implementations do the same.** The finding rests on pp. 23, 32 and 33, not on any implementation, and none of the four cites a measurement of $E2 itself; Copperline names a source for its two-count lead, *"confirmed against the real-A500 vAmigaTS spritedma/interfere photos"* ([`copper.rs:104-131`](https://github.com/CopperlineHQ/Copperline/blob/726bed00c407727c1f5bd32c7193587986638941/src/chipset/copper.rs#L104-L131)).
- **No page says on which colour clock the Copper notices a true comparison**, and the package's two readings of the Copper's cycle parity (A and B) are left open; the 3 at $E2 lies outside both.
- **Hardware not measured.** Does a real Agnus end `$FFE3,$FFFE` on line 255? On a PAL machine: a list that waits for ($FF,$E2) and then changes COLOR00, followed by `$FFFF,$FFFE`. A colour change at the end of line 255 or the start of line 256 settles it for p. 23; none before the next field settles it for the four.
- **Does p. 33's loop work?** Its `$00E3,$80FE` masks the vertical position but VP7, so on lines 0 to 127 it can end only when the horizontal count reaches $E2. If a short line never shows $E2 to a pending WAIT — as in NanoMig and, by their sources, in all four — that WAIT does not end before line 128, and the loop does not interrupt every 16 lines. This is not measured.
- **Long NTSC lines.** p. 23 gives an NTSC long line the counts 0 to $E3, and $E3 compares as $E2. Once NanoMig has long lines ([NM-HRM-010](NM-HRM-010.md)), whether the WAIT ends on a long line 255 is the same question for one line in two.

## Decision

**One option: hold the comparator's result while the WAIT is pending**, so that a match lasting one count is not lost before the state machine can act on it. In line 308:

```verilog
-  		if ({vpos[7:0],hpos[8:2]} >= {vercmp[7:0],horcmp[8:2]}) 
+  		if ({vpos[7:0],hpos[8:2]} >= {vercmp[7:0],horcmp[8:2]} || (beam_match && copper_state==WAITSKIP2))
```

By the code, not run by `make test`: the match seen at count 1 of line 256 is held, blocked at count 2 and acted on at count 3, which is 163 counts after count $43 of line 255, where the WAIT for $40 ends; 163 is one of the two values reading A of the cycle parity gives. A private copy of the chip set with this change (the package's `wait_e2.patch`, not run by `make test`) prints, for the package's run B, 36 passed, 0 failed on fx68k and on TG68K, and `P6-LARGEST PAL` and `P6-LARGEST NTSC` pass with x_0 fetched 163 slots after a_0. Also by the code: a WAIT whose comparison becomes true and false again before the state machine acts — the last count of a line, or a masked position the beam passes — ends instead of waiting for the next match; p. 33's `$00E3,$80FE` would end on the line it is fetched on, and a list that ends with `WAIT($FF,$E2)` where `$FFFF,$FFFE` is meant would run on past line 255. This puts NanoMig against all four implementations; it is not proposed as obviously correct. The page closes as *What is asked of a reader* says.
