# Specification — `appK-autoconfig-register-map`

Package: `hrm/appK-autoconfig-register-map`
Fixture (top module, per task assignment): `cpu_wrapper`
Claims file: `hrm-testpipeline/work/appK-build/appK-autoconfig-register-map.jsonl`
(47 claims, printed pages 432–434, Appendix K, "REGISTER BIT ASSIGNMENTS" /
Appendix K's Zorro-II/Zorro-III AUTOCONFIG register table)

## Disclosure on the write-order

The task brief for this package itself required answering, before any test
could be designed, whether `cpu_wrapper` can be driven at all from outside —
its bus ports (`chip_addr`, `chip_din`, `chip_rw`, `chip_uds`, `chip_lds`,
`chip_as`) are all `output`/`output reg`, generated by whichever CPU core the
module instantiates internally, from real instruction execution. A prior
package in this suite (`hrm/ch1-cpu-and-instruction-cache`) had already
measured that the default core (`fx68k`, `nanomig/src/fx68k/fx68k.sv`) does
not elaborate under this project's pinned Verilator (5.052): `%Error-
BLKANDNBLK` on `fx68k.sv:293`, an unsupported blocking/non-blocking mix. This
package's own task brief flagged the same practical risk and required it be
resolved (build what's reachable, decline what isn't, and say precisely which
boundary would answer a declined claim) before the 47 claims could be
assigned to `expect()` or `record()`. Resolving that required opening
`cpu_wrapper.v` and running real Verilator builds — the "write the spec blind,
then open the RTL" order was broken for this reason, disclosed here rather
than presented as if it held, exactly as `ch1-cpu-and-instruction-cache`'s own
`SPECIFICATION.md` disclosed the same break for the same underlying reason.
The claims file's own `classify.evidence` field also already carries
`file:line` RTL citations on every one of the 47 claims (added by the
classifier before this build started), which is the second, independent
reason this agent already possessed RTL knowledge before writing propositions
— again the same situation `ch1-cpu-and-instruction-cache` disclosed. What
follows keeps the substantive discipline the order protects: expected values
below are cross-checked against the RTL's own text (case-statement literals
and their own comments), not copied from `classify.evidence`'s prose.

## Boundary investigation — measured, not assumed

1. **`fx68k` (the default core, selected when neither `ENABLE_TG68K` nor
   `ENABLE_FX68K` is defined) does not elaborate.** Re-measured directly for
   this package:
   `verilator --lint-only --top-module cpu_wrapper cpu_wrapper.v fx68k.sv
   fx68kAlu.sv uaddrPla.sv` → `%Error-BLKANDNBLK: fx68k.sv:293:10:
   Unsupported: Blocking and non-blocking assignments to same non-packed
   variable: 'cpu_wrapper.cpu_inst_o.Nanod'` — `%Error: Exiting due to 1
   error(s)`, reproduced with `-Wno-fatal` too (a genuine `Error`, not a
   waivable `Warning`). This confirms the prior package's finding still
   holds on this pinned checkout.

2. **`TG68KdotC_Kernel` (the other core `cpu_wrapper.v:38-42`/`:403-470` can
   select, via `` `define ENABLE_TG68K``) does elaborate, and is the one this
   package uses.** `cpu_wrapper.v`'s own `` `ifdef VERILATOR `` branch
   (`:420-440`) binds an all-lowercase port list matching exactly
   `nanomig/sim/TG68KdotC_Kernel.v` (not the parametrized synthesis source at
   `nanomig/src/tg68k/verilog/TG68KdotC_Kernel.v`) — i.e. the pinned RTL
   itself already anticipates and names a Verilator-compatible build of this
   core; this package does not substitute a materially different
   implementation the way a hand-adapted fork would. `verilator --lint-only
   -Wno-fatal -DENABLE_TG68K=1 --top-module cpu_wrapper cpu_wrapper.v
   sim/TG68KdotC_Kernel.v` → zero `%Error` lines (12 warnings, all
   `UNSIGNED`/`UNOPTFLAT`, none fatal). `TG68KdotC_Kernel` is also not a
   board-specific choice invented for this test: `grep` across every real
   board top-level in the pinned submodule
   (`src/lattice/icepi-zero/top.sv`, `src/lattice/icesugar-pro/top.sv`,
   `src/mistle/gw3a_20/top.sv`, `src/mistle/gw5a_25/top.sv`,
   `src/tang/nano20k/top_020.sv`) shows `` `define ENABLE_TG68K`` already set
   for 5 of 6 shipped targets — including both AGA-capable ones, with the
   comment "required for AGA as that expects a 020 cpu" — so this is the CPU
   core real NanoMig hardware actually runs with for this `minimig-aga`
   variant, not an artifact chosen only to make Verilator happy.

3. **A real, hand-assembled 68000 program, executed by this core through
   `cpu_wrapper`'s own genuine ports, does reach the AUTOCONFIG window and
   round-trips real data.** Built and ran (see below) a throwaway spike:
   reset vectors at `$000000`/`$000004` point at a 3-instruction program
   (`MOVE.W ($E80000).L,D0` / `MOVE.W D0,($002000).L` / `BRA.S *`) supplied
   entirely through `chip_dout`+`chip_dtack` (the module's own bus-response
   inputs — `ramsel` is held permanently false by tying `turbocfg=0`, so
   every access, vector fetch, instruction fetch, AUTOCONFIG read and scratch
   write alike, is served through the `chip_as`/`chip_uds`/`chip_lds`/
   `chip_rw`/`chip_dtack` protocol at `cpu_wrapper.v:658-704`, never through
   the internal RAM path). Result, captured purely by watching `chip_addr`/
   `chip_rw`/`chip_din` (genuine output ports) for a write to `$002000`:
   `data=E000` — the exact upper nibble (`E`=`1110`) the RTL's own case
   arm for register 00 in Zorro-II mode computes
   (`cpu_wrapper.v:563 6'b000000: autocfg_data = 4'b1110;`), delivered by a
   real reset → vector-fetch → instruction-fetch → decode → execute → bus
   read → bus write sequence, no internal signal touched. Repeated with
   `cpucfg[1]=1`+`fastramcfg[2]=1` (selects the Zorro-III case branch,
   `cfg_z3` at `cpu_wrapper.v:535`): same scratch write, `data=A000`, matching
   `cpu_wrapper.v:585 6'b000000: autocfg_data = 4'b1010;`. **This is a
   working boundary: no debug port, no internal force, only `cpu_wrapper`'s
   own ports (`chip_dout`/`chip_dtack`/`chip_ipl`/`cpucfg`/`fastramcfg`/
   `chipramcfg`/`slowramcfg`/`turbocfg`/`bootrom`/`reset`/`clk`/`ph1`/`ph2` as
   inputs; `chip_addr`/`chip_din`/`chip_as`/`chip_uds`/`chip_lds`/`chip_rw`/
   `cpustate`/`cpu_clkena` as observed outputs).** One measurement pitfall
   corrected along the way, kept here because it explains why the first two
   attempts hung: `reset` on this module is **active-low**
   (`cpu_wrapper.v: always @(posedge clk, negedge reset)`, `if (~reset |
   ~reset_out)` throughout, `.nreset(reset)` direct wiring into the TG68K
   core) despite its plain name — driving it the conventional active-high way
   holds the design permanently in reset once released.

4. **`ph1`/`ph2` timing.** `cpu_wrapper`'s own ports, driven directly by this
   fixture, not through `nanomig.v`'s `amiga_clk` PLL (irrelevant off this
   module's own boundary). `nanomig.v:144-179`'s comment table gives the real
   relationship (`ph2` pulses once, then `ph1` once, every 4 `clk` edges);
   this fixture reproduces that 4-edge cadence directly in the C++ driver
   without instantiating `amiga_clk`. `chip_dtack` is tied constant asserted
   (active low, `0`) throughout — every chip-bus cycle in this fixture
   completes in the RTL's own minimum number of stages
   (`cpu_wrapper.v:658-704`'s `stage` 0→1→2→3); no wait-state timing is
   modeled or needed for register-content claims.

## The register-map arithmetic this package relies on

Every AUTOCONFIG read in this RTL delivers one 4-bit nibble
(`autocfg_data`, `cpu_wrapper.v:229`) in bits 15:12 of the word read at
`$E80000 + 2*chip_addr[6:1]`; bits 11:0 pass the fixture's own `chip_dout`
straight through and carry no RTL-driven register content. Confirmed by
reading `cpu_wrapper.v:559-598` (the `autocfg_card`-guarded case block; the
`` `ifdef ENABLE_TOCCATA`` block at `:543-556` is not compiled into this
build and is not used) against its own comments:

- **`chip_addr[6:1]` 0 and 1 carry the *direct*, uninverted logical value.**
  Confirmed two independent ways: (a) register 00's high nibble at index 0
  (`4'b1110` Zorro-II / `4'b1010` Zorro-III) reads directly as bits 7:6 =
  `11`/`10` — the exact Zorro-II/Zorro-III type codes the page states,
  matching the RTL's own comments (`// Zorro-II card, add mem, no ROM` /
  `// Zorro-III card, add mem, no ROM`) with no inversion; (b) index 1's
  Zorro-II value (`cpu_wrapper.v:566-572`, selected by `fastramcfg_d`:
  `4'b0110`/`4'b0111`/`4'b0000`) reads directly as bits 3:2:1:0 =
  `[related=0, size=110/111/000]` — `110`,`111`,`000` are exactly the real
  Zorro-II board-size codes for 2 MB / 4 MB / 8 MB, matching the RTL's own
  `// 2MB`/`// 4MB`/`// 8MB` comments only if read direct, not complemented.
- **Every other `chip_addr[6:1]` index (2, 4, 8, 9, 10, 11, 19/`0x13`, and
  every unmapped index that falls to the `default: autocfg_data = 4'b1111`
  at `:541`) carries the *one's complement* of the logical value.** Confirmed
  the same way, against the RTL's own comments: manufacturer number, indices
  8/9/10/11 (`4'b1110`,`4'b1100`,`4'b0110`,`4'b0011`) complement to
  `0001`,`0011`,`1001`,`1100` → byte pair `0x13`,`0x9C` → **`0x139C`**,
  exactly the RTL's own comment (`// Manufacturer ID: 0x139c`,
  `cpu_wrapper.v:574`). Product ID, index 2, Zorro-III only (`4'b1110`)
  complements to `0001`, matching `// ProductID=0x10 (only setting upper
  nibble)` (`:587`) — nibble `0001` is exactly the high nibble of `0x10`.
  Register 08 flags, index 4, Zorro-III only (`4'b0000`) complements to
  `1111`, matching `// Memory card, not silenceable, Extended size,
  reserved.` (`:588`) bit-for-bit (bit7=1 memory, bit6=1 not-silenceable,
  bit5=1 extended, bit4=1 reserved-must-be-1). Serial number, index 19/`0x13`
  (`4'b1110` Zorro-II / `{2'b11,~autocfg_card}` Zorro-III) complements to
  `0001`, matching `// serial=1` / `// serial=1/2` (`:578`,`:594`). Register
  0C, indices 6/7 (unmapped, default `4'b1111`) complements to `0000`,
  matching the page's own "Reserved, must be 0". Every one of these five
  independent cross-checks against the RTL's *own* comments agrees only
  under the complement rule — this is not an assumption carried in from
  `classify.evidence`, it is re-derived here from the case-statement text
  itself.
- **This RTL reuses the same `$E80000`-`$E8007E` window for its "Zorro III"
  case branch** (selected by `cfg_z3 = fastramcfg_d[2] & cpucfg[1]`,
  `cpu_wrapper.v:535`), not a distinct `$E80100`+ decode. `chip_addr[6:1]`
  is 6 bits wide (max byte offset `0x7E`); `sel_autoconfig`
  (`cpu_wrapper.v:601`) only ever matches `chip_addr[23:16]==8'b11101000`
  (`$E8xxxx`). The literal Zorro-III addresses several claims quote
  (`100`,`104`,`108`,`110`,`114`,`118`,`11C`,`120`,`124`) are therefore never
  reached by this design's own decode at any input this fixture can drive —
  its "Zorro III" register *content* lives at the *same* low offsets as
  Zorro II, gated by `cfg_z3` instead of a distinct address match. This
  matters for the three claims whose entire assertion is that literal
  address triple with no accompanying bit-content (see "Declined claims"
  below).

## Declined claims (5), and the boundary that would answer them

- **`sol:K-0768`, `opus:K-0791`(page 432)** — "the Zorro III register 08 may
  modify the size of the linked memory" is a *causal/reactive* claim (varying
  register 08's content changes the computed logical size). This RTL
  implements register 08 (index 4) and the "logical size" register (index 5)
  as independent, static case-statement constants — neither is a function of
  the other, and register 08 has no write handler at all
  (`cpu_wrapper.v:619-646` only handles writes to indices `0x24`/`0x22`, the
  RAM-activation registers, never index 4) — there is no live "modify"
  mechanism in this design to observe. Declined: `unreachable-behaviour`,
  named at `cpu_wrapper.v:588-589` (both constants, no producer/consumer
  relationship between them).
- **`opus:K-0784`(page 432), `opus:K-0812`, `opus:K-0815`(page 433)** — each
  of these three claims' *entire* content is a literal `logical=ZII=ZIII`
  address triple, with no accompanying bit-content assertion to fall back on
  (contrast `sol:K-0762`, which states the same triple but *also* states the
  bit-7:6 content, graded in Group A on the content). Per "The register-map
  arithmetic" above, the quoted Zorro-III address (`100`/`104`/`108`) is
  never reached by this design's own `sel_autoconfig` decode at any
  `chip_addr` this fixture — or any fixture built on this module's own ports
  — can drive. Declined: `unreachable-address`, named at `cpu_wrapper.v:601`
  (`sel_autoconfig` only ever matches `$E8xxxx`, and `chip_addr[6:1]` cannot
  represent an offset at or beyond `0x100`).

## What this build actually does

Two configurations of the same fixture are run to completion, each a real
reset → 68000 program → AUTOCONFIG reads → scratch writes sequence through
`cpu_wrapper`'s own ports only:

- **Zorro II** (`cpucfg=0`, `fastramcfg=1`, `cfg_z3=0`): indices 0, 1, 4, 6,
  8, 9, 10, 11, 12, 14, 16, 18, 19.
- **Zorro III** (`cpucfg=2` [bit1=1], `fastramcfg=4` [bit2=1], `cfg_z3=1`):
  indices 0, 1, 2, 3, 4, 19.

Each index's raw nibble is captured from a genuine bus write (the CPU core's
own `MOVE.W D0,(scratch).L`, observed on `chip_addr`/`chip_rw`/`chip_din`)
after a genuine bus read (`MOVE.W (target).L,D0`) of that index — never an
internal signal. The direct/complement rule above converts each raw nibble to
its logical value before grading against the page.
