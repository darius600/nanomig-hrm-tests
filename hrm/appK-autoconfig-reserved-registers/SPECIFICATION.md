# Specification — `appK-autoconfig-reserved-registers`

Package: `hrm/appK-autoconfig-reserved-registers`
Fixture (top module, per task assignment): `cpu_wrapper`
Claims file: `hrm-testpipeline/work/appK-build/appK-autoconfig-reserved-registers.jsonl`
(34 claims, printed pages 435-436, Appendix K, "REGISTER BIT ASSIGNMENTS" table's
run of reserved registers between the serial-number block and the base-address /
shut-up registers)

## Disclosure on the write-order

This package inherits its fixture wholesale from the sibling package
`hrm/appK-autoconfig-register-map`, which already did the hard work of
establishing that `cpu_wrapper` can be driven from outside at all: its bus
ports (`chip_addr`, `chip_din`, `chip_rw`, `chip_uds`, `chip_lds`, `chip_as`)
are all `output`/`output reg`, generated by whichever CPU core the module
instantiates, and the default core (`fx68k`) does not elaborate under this
project's pinned Verilator (`%Error-BLKANDNBLK`, `fx68k.sv:293`). The sibling
package measured this, selected `TG68KdotC_Kernel` (`` `define ENABLE_TG68K``,
built from `nanomig/sim/`) as the working alternative, and built a hand-
assembled 68000 program driven through `cpu_wrapper`'s own ports (reset,
`chip_dout`/`chip_dtack` responses, `ph1`/`ph2` cadence) to reach the
AUTOCONFIG window. This package reuses that fixture design (the `Harness`
struct, its reset/clock/bus-response protocol, and the read-then-scratch-
write technique) without re-deriving it. As with that package, the claims
file's own `classify.evidence` field already carries `file:line` RTL
citations on all 34 claims (added by the classifier before this build
started), so the "write the spec blind, then open the RTL" order is broken
for the same reason disclosed there — disclosed here rather than presented
as if it held.

## What these 34 claims assert

Every claim in this package has the same shape: "Logical register `XX` bits
7-0 are reserved and must be 0", for the 17 distinct logical registers that
fall in the gap between the serial-number block (register 24, last
implemented read register) and the base-address/shut-up registers (44, 48,
4C, handled by `hrm/appK-autoconfig-base-address`):

- Page 435: registers 30, 34, 38, 3C, 40 (5 registers)
- Page 436: registers 50, 54, 58, 5C, 60, 64, 68, 6C, 70, 74, 78, 7C (12
  registers)

Each register is claimed twice (once by reader `sol`, once by reader
`opus`), 17 × 2 = 34.

## The register-map arithmetic this package relies on

Inherited unchanged from `hrm/appK-autoconfig-register-map`'s
SPECIFICATION.md ("The register-map arithmetic this package relies on"),
re-cited here rather than re-derived:

- Every AUTOCONFIG read delivers one 4-bit nibble (`autocfg_data`,
  `cpu_wrapper.v:229`) in bits 15:12 of the word read at
  `$E80000 + 2*chip_addr[6:1]`.
- `chip_addr[6:1]` indices 0 and 1 carry the *direct* (uninverted) logical
  value; every other index carries the *one's complement*.
- The unconditional default is `cpu_wrapper.v:541 autocfg_data = 4'b1111;`,
  which under the complement rule reads as logical `0000` — exactly
  "reserved, must be 0".

## Boundary investigation — which indices these 34 claims land on

Each logical register `XX` (a hex byte value, e.g. `30`) is served as two
consecutive 16-bit words: the high nibble at `$E8XX` (`chip_addr[6:1] =
XX/2`) and the low nibble at `$E8(XX+2)` (`chip_addr[6:1] = XX/2 + 1`) —
established by `hrm/appK-autoconfig-register-map`'s own reading of register
00 (`cpu_wrapper.v:563`/`:564`, indices 0 and 1) and reused here without
re-deriving it. Computed for all 17 registers:

All 34 indices are within the legal 6-bit range of `chip_addr[6:1]`
(0-63, i.e. byte offsets $00-$7E, `hrm/appK-autoconfig-register-map`'s own
"max byte offset 0x7E" finding). None of them appears in either case list
(`cpu_wrapper.v:562-580` Zorro II: indices 0,1,8,9,10,11,19 only;
`cpu_wrapper.v:584-596` Zorro III: indices 0,1,2,4,5,8,9,10,11,19 only) —
every one of the 34 indices this package reads therefore falls to the
unconditional `cpu_wrapper.v:541` default, regardless of `cpucfg`/
`fastramcfg`. This is config-independent by construction, so a single
Zorro-II-configured harness (`cpucfg=0`, `fastramcfg=1`) is sufficient
evidence for all 34 claims — there is no Zorro-III-only or Zorro-II-only
divergence to chase here, unlike the base-address package.

## What this build actually does

One harness, one configuration (Zorro II, `cpucfg=0`, `fastramcfg=1`),
reads both nibbles of all 17 registers through a real reset → 68000
program → AUTOCONFIG read → scratch-write sequence, identical in mechanism
to `hrm/appK-autoconfig-register-map`. Each register's byte is assembled
from its two nibbles (both expected `0x0` after the complement rule) and
graded as `0x00`.

## Expected outcome

Every one of the 34 claims is expected to grade PASS: `cpu_wrapper.v:541`'s
default is unconditional and hard-coded, and no case arm in either branch
ever touches any of these 34 indices (verified above by reading the full
case-statement text, not assumed). This package therefore does not carry a
candidate finding — it is included for completeness of the appendix's
reserved-register table, and its value is in being enumerated, not in
producing a divergence. Unlike `hrm/appK-autoconfig-base-address`, there is
no expectation of red here going in, and none is being manufactured.

No claims are declined in this package: all 34 are directly observable at
`cpu_wrapper`'s own ports with no internal signal touched.
