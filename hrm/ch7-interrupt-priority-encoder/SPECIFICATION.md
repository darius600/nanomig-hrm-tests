# Specification: ch7-interrupt-priority-encoder

Fixture: `paula_intcontroller`. Subject: the interrupt priority encoder --
which 68000 hardware interrupt level each of the interrupt request
register's sources drives, the pin-to-bit map for the two external
interrupt lines, and arbitration between sources.

Written from the quotations in `ch7-interrupt-priority-encoder-spec-stage.jsonl`
alone, plus Figure 7-4 (`docs/references/amiga-hrm-3rd/ch7/figures/p221.png`),
which the task sheet names as source material proper to step 1 because it is
a rendered manual page, not RTL. No RTL has been opened to produce this
document. Every claim is cited by its `uid` (`<reader>:<id>`), never by the
bare `id`, per BUILD-BRIEF.

**A note on the claims file itself.** Several records' `classify.note` and
`classify.split.asserted` fields (e.g. the entries behind P4, P7's and P14's
denotation claims, and the naming-conflict entries) contain RTL port names,
signal names and `paula_intcontroller.v` line numbers, despite the task
sheet's description of this file as scrubbed of exactly that content for
step 1. None of that material is used below -- every proposition is phrased
in the manual's own vocabulary (register bit numbers, the mnemonics printed
on pages 219-221, and 68000 interrupt levels), never in the RTL's. This
did not amount to a HALT: a testable specification does not need the port
names to say "bit 3" or "PORTS." It is flagged in the message to the lead
so the leak itself can be looked at.

## Chipset scope

Every one of the 96 claims in the claims file carries the same chipset
finding: `applies_to: [OCS, ECS]`, `differs_ocs_ecs: false`, justified at
printed p.224 ("ECS system control. For information on the system control
registers in the Enhanced Chip Set (ECS), see Appendix C.") together with a
grep of Appendix C showing no INTENA/INTENAR/INTREQ/INTREQR entry anywhere
in it. The interrupt controller is therefore unchanged by ECS, and every
proposition below is asserted once, for both chipsets, on the same fixture
run.

## Testable propositions

### Global level range

#### P1 -- The module's achievable output levels are exactly 1 through 6

> "The various kinds of interrupts generated by the hardware are brought
> into the peripherals chip and are translated into six of the seven
> available interrupts of the 680x0." (printed p.217)

> "Interrupt levels 1 through 6 are generated." (printed p.217)

Testable form: across an exhaustive sweep of the interrupt request
register's bit patterns (with the corresponding enables set), the module's
output level takes every value in {1,...,6} for some pattern, and no
pattern of this module's own sources produces a level outside that set
(level 0, i.e. "no interrupt", is not itself a level and is not asserted by
this proposition -- see P2 for level 7).

Cited by: `sol:7-interrupts.c1`, `opus:7-int.c2` (twin, same proposition),
`sol:7-interrupts.c4`, `opus:7-int.c5` (twin, same proposition, the specific
1-through-6 enumeration).

Report-only, not folded into P1's assertion: `opus:7-int.c1` reads "This
system supports the full range of 680x0 processor interrupts" (printed
p.217) and is itself flagged report-only by the claims file's own
classification, because "full range" is disputed against the very next
clause on the same page (level 7 is never generated -- P2). Its undisputed
half is P1's content already; asserting "full range" literally would demand

#### P3 -- Every bit of the interrupt request register is independently settable through the register bus

> "The Copper can change the content of any of the bits of this register,
> as it can write any value into most of the machine registers." (printed

## Priority arbitration between sources

The task sheet's subject line for this package names "arbitration between
sources" as part of what it covers. Two distinct behaviors are in view:

1. **Sources that share one hardware level** (level 1: bits 0/1/2; level 3:
   bits 4/5/6; level 4: bits 7/8/9/10; level 5: bits 11/12; level 6: bits
   13/14) do not need to be "arbitrated" against each other in the sense of
   picking a winner -- the 3-line IPL bus cannot distinguish which specific
   bit within a level is pending; any one of them, or several together, at
   the same level produces that level's IPL value. Testing each bit
   individually (P5-P19) and confirming no bit produces a level outside
   its documented one already establishes this.
2. **Sources at different levels pending simultaneously** must be encoded
   down to a single IPL value, standardly the numerically highest pending
   level on a 680x0. No claim in this package's claims file states this
   rule from a printed quotation -- none of the 96 records quotes a
   sentence to the effect of "the highest pending level is presented to
   the processor." Per BUILD-BRIEF ("where the manual is silent, measure
   and report -- do not assert"), this behavior is not asserted as a
   proposition of this specification. It will be measured in the fixture
   (multiple bits at different levels set together, observing which level
   the module presents) and reported via `note`, not graded via `expect`,
   unless a printed quotation for it surfaces on opening the RTL header
   comments or a neighbouring package's claims -- which would not license
   asserting it here either, since this package's own claims file does not
   carry that quotation.

## Control case

BUILD-BRIEF requires at least one control case expected to PASS on the same
measurement basis as any case under suspicion. This package's 15 per-bit
propositions (P5-P19) already supply this structurally: all fifteen are
measured the same way (set one bit through the register bus per P3, enable
it, read the module's output level) but expect fifteen different pairings
across six distinct level values (1, 2, 3, 4, 5, 6) and one exclusivity
fact (P8). A fixture that always reported a fixed level, or that failed to
discriminate between bits, would be caught by disagreement among these
fifteen differently-valued expectations -- exactly as
`ch7-vertb-vertical-blank-timing`'s NTSC/PAL constants (20 vs. 25 lines)
cross-check each other from the same code path. P1/P2's exhaustive sweep
(every one of levels 1-6 reachable, level 7 never) is a second, independent
cross-check over the same output.

## Precondition to assert

Per BUILD-BRIEF's fixture-integrity rule (the module whose DMA grant was
sampled in the same `eval()` as the request, reporting a false `zero`-flag
defect, is the cautionary case named in the brief), a green on any of
P5-P19 depends on this fixture's register-bus write to the interrupt
request register actually being visible to the priority-encoding logic
before its result is sampled -- not silently absorbed, delayed past the
sampled cycle, or read back as a different bit than the one written. Where
that has never been shown, it does not get to stay an assumption: the
package must assert, as its own precondition proposition, that a
register-bus write of a known, distinct bit pattern to the interrupt
request register is correctly read back (via the request register's own
readback path) before any P1-P19 assertion is trusted. Per P3, this
precondition is also the direct empirical basis for that proposition (all
32768 patterns reachable) -- the two are proven by the same measurement.
This precondition is not itself sourced from a manual quotation; it is
asserted as an engineering precondition, not cited to a page.
