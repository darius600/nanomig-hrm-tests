# Specification: Copper MOVE package

This document specifies an integration test package for the Copper MOVE
instruction and the registers it is tied to: the Copper location registers,
COPCON, and the location-register restart rule that Appendix B also applies to
audio. It was written from the package's claims (`claims-spec-stage.jsonl`) and
the pages of the *Amiga Hardware Reference Manual*, 3rd edition, by an author
who never saw the implementation or any test. Page numbers are printed page
numbers. Where the electronic page text and the printed page could differ, the
printed page was rendered and read.

The package has eight propositions (P1 to P8). Section 1 lists the claims that
could not be turned into a proposition. Section 2 lists where the pages
disagree or leave a value open. Section 3 defines the setup and observation
rules that all propositions share. Section 4 holds the propositions. Section 5
maps every claim id to a proposition or to a reason for declining it.

## 2. Where the pages disagree or leave a value open

1. **Which registers the Copper may write.**
   - p.21: "Any register whose address is $20 or above." / "Any register whose
     address is between $10 and $20 if the Copper danger bit is a 1." / "The
     Copper cannot write into any register whose address is lower than $10."
   - p.26: "The registers that the Copper can always affect are numbered $80
     through $FF inclusive. ... Those it cannot affect at all are numbered $00 to
     $3E inclusive. ... The rest of the registers, from $40 to $7E, are protected
     by a bit in the Copper control register." / "When CDANG is 0, these
     registers cannot be written by the Copper. When CDANG is 1, these registers
     can be written by the Copper."
   - p.287 legend: "* Address not writable by the Copper." / "~ Address not
     writable by the Copper unless the "copper danger bit", COPCON is set true."
     p.289-290 mark $000-$03E with * and $040-$07E with ~, which matches p.26.
   - p.310 (ECS): "In the standard chip set, if this is set, the Copper can
     access the address range from $DFF03E through $DFF07E. Now, in the ECS, if
     this bit is set, the Copper can access all of the Amiga chip registers. If
     this bit is clear, the Copper can access the address range from $DFF03E
     through $DFF07E, the same range as when the danger bit is set in the
     standard chip set."

   No page contradicts three points, and every page that speaks to them
   states them: the Copper can write $080-$0FE; it can write $040-$07E when
   CDANG = 1; and it cannot write below $010 when CDANG = 0. This package uses
   only the first two. The pages share no outcome for CDANG = 0 in $010-$07E,
   or for CDANG = 1 in $010-$03E, so neither is specified.

2. **Registers above $0FF.** p.26 lists only "$80 through $FF" as always
   writable. Other pages show the Copper writing above $0FF: p.21 allows "$20 or
   above"; p.19 says the Copper can "change the color palette"; p.27 has "MOVE
   firstcolor1 to COLOR17"; the p.29 list writes BPLCON0 ($100) and COLOR00-03
   ($180-$186); and p.290-292 put no * or ~ mark on any address above $07E.
   P1, P3 and P4 write COLOR00 ($180) from the Copper and rely on these pages.
   Read literally, p.26 leaves $100-$1FE unclassified. Its own phrase "The rest
   of the registers, from $40 to $7E" implies that its three groups cover all
   registers.

3. **Width of COPxLCL.** p.25 lists "COP1LCL Low 16 bits of first Copper list
   address". The p.25 text says "contains the least significant data, or low 15
   bits of the address", and p.273 and p.290 say "(low 15 bits)". Specified
   here: bits 15-1 only. These are the bits every page covers and the only ones
   a word address shows.

4. **Width of COPxLCH.** p.25: "High 3 bits". p.273 and p.290: "(high 3 bits,
   high 5 bits if ECS)". p.309: "(high 5 bits,was 3 bits)". Specified here:
   bits 2-0 only, with bits 15-3 written as 0, so every list address is below
   $80000.

5. **When the vertical-blank restart happens.** p.25: "At the start of each
   vertical blanking interval, COP1LC is automatically used to start the
   program counter. That is, ... when the end of vertical blanking occurs, the
   Copper is automatically forced to restart". p.30: "When the screen display
   ends and vertical blanking starts, the Copper will automatically be pointed
   to the top of its instruction list". p.32: "at the start of the vertical
   blanking period". p.276: "at the beginning of each vertical blank time". No
   check in this package depends on the moment of the restart. P1 allows for
   either reading (P1, item 4).

6. **How the strobe is hit.** The p.30 example uses a read:
   "MOVE.W COPJMP1(a1),d0 ; Causes copper to load PC from COP1LC". p.25 ("When a
   jump address strobe is written"), p.276 ("When written to, they cause the
   Copper to jump") and p.287 ("Writing the register causes the effect") all
   say written. This package writes the strobe, which every page covers.

7. **Where the COPINS bit table is printed.** The claims cite the MOVE/WAIT/SKIP
   bit table of Appendix A as p.274, from the electronic page text. In the
   printed edition the table is on p.275, under the heading "COPINS (cont.)".
   The printed page was rendered and read. Its MOVE columns (X / DA8-DA1 / 0 and
   RD15-RD00) match the electronic text and Table 2-2 on p.36 word for word.
   This is a placement difference, not a difference in content.

Values the pages leave open. No test may grade these:

- COLORxx bits 15-12: "Unused" (p.46, Table 3-3), "X" (p.273).
- MOVE IR1 bits 15-9: "Not used" (p.21), "X = don't care" (p.36).
- Location-register bits beyond the widths in items 3 and 4.
- The value read from any write-only (W) register (p.287 "W=write-only").
- The delay from a register write to its pixel on the video output, and the
  delay from a WAIT being satisfied to the following MOVE. Neither is stated.
- What COPCON bit 1 = 0 allows in $010-$07E (item 1).
- Whether the Copper fetches the word after an end WAIT's second word before
  it restarts (Section 8, A1). The printed pages do not say.
- Whether the Copper fetches the words of a MOVE that stands behind a WAIT
  that is never satisfied (Section 8, A2). The pages say only that the MOVE is
  not performed.

## 3. Shared definitions

**System.** PAL, Enhanced Chip Set, 2 MB Chip memory, the 68000 core, unless a
proposition says otherwise. Every address used below is under $80000, so all
location registers stay inside the 3 high bits that all pages agree on.

**Register addresses.** A custom register is at $DFF000 plus the offset given
in Appendix B. p.310 writes the Copper range as "$DFF03E through $DFF07E", and
p.29 note 3 says Copper destination addresses "are offsets from the base
address of the custom chips".

**Baseline (every program, first).** DMACON ← $7FFF, INTENA ← $7FFF,
INTREQ ← $7FFF. On p.278 and p.280, bit 15 = 0 clears the bits written as 1,
so these writes turn off all DMA, interrupt enables and requests. Then the
program writes marker 0. Propositions that look at the video also write
BPLCON0 ← $0200 (p.48: BPU = 000 "Shows only a background color"; p.29 uses
bit 9 "coloron") and SPRxCTL ← $0000 for x = 0..7 at $DFF142 + 8x (p.123: "The
sprite can be terminated ("disarmed") by writing to the SPRxCTL register").

**Markers.** A marker is a CPU word write of a step number to a reserved
Chip-memory word ($4F000). It appears at the Chip-memory port as a CPU write
with a timestamp. Because the CPU executes in program order, each register
write precedes the marker written after it.

**Copper list encoding.** All Copper lists are in Chip memory (p.20; p.29
note 1). Each instruction is two words at consecutive addresses (p.20).
- MOVE: IR1 = the register offset, with bit 0 = 0, bits 8-1 = DA and bits
  15-9 = 0 (p.21). IR2 = the data (p.21, p.36).
- WAIT for line v with the horizontal position ignored: `$vv01,$FF00`. This
  follows the p.23 example `$9601,$FF00`, with BFD = 1 as is normal (p.22,
  p.35).
- End of list: `$FFFF,$FFFE`. p.23: "This event will never occur, so the
  Copper stops until the next vertical blanking interval begins". p.30 says the
  same.

**Copper start sequence S(T)**, following p.30 ("you must initialize one of
the Copper location registers ... and write to its strobe address before
Copper DMA is turned on"):
`MOVE.L #T,$DFF080` (COP1LC; p.25 "you write the 18-bit address by moving one
long word to the register whose name ends in "H""), then a marker, then
`MOVE.W #0,$DFF088` (COPJMP1, written), then a marker, then DMACON ←
$8000|$0200|$0080 plus any further enable bits the proposition names (p.278:
SET/CLR, DMAEN, COPEN), then the **enable marker**. The Copper starts as soon
as Copper DMA is on, so it can read before the enable marker is written
(Section 8, A3).

**Access attribution.** The harness description says the test sees "every DMA
fetch (Copper instruction fetches, bitplane, sprite, audio, disk, refresh,
blitter) and every CPU access". This specification uses that attribution: a
*Copper access*, *blitter access*, *audio channel 0 access* or *CPU access* is
an access the harness attributes to that channel. If the harness cannot
attribute accesses, the propositions cannot be built as specified. A builder
must not replace attribution with an address-range rule without saying so.

**Restart access and pass.** The *extra read* is a Copper read at the word
directly after an end WAIT's second word ($FFFE), made after the read of that
second word and before the next restart. It is printed as a MEASURED line and
belongs to no pass (Section 8, A1). A *restart access* is the first Copper
access after the Copper has read the second word ($FFFE) of its list's end WAIT
that is not the extra read. While
waiting, the Copper "does not use the memory bus at all" (p.19; p.22 "the
Copper is off the bus"), so this access is where the Copper restarts at
vertical blank (p.25, p.30). The moment of the restart is not used (Section 2,
item 5). A *pass* is the run of Copper accesses from one restart access up to
and including the read of the end WAIT's second word. Every list start in the
stimuli lies away from the word after an end WAIT.

**Video sampling.** A *field* is the output between two consecutive VSYNC
pulses. A *row* is the output between two consecutive HSYNC leading edges. The
*row sample* is the 4-bit R, G, B value at the pixel clock halfway between the
row's two HSYNC leading edges. That point lies in the visible middle of the
line, far from the line start, where a WAIT with the horizontal position
ignored releases its MOVE. *Black* is (0,0,0). The *run sequence* of a field is
the sequence of its non-black row samples with consecutive equal values
collapsed into one. The line doubler duplicates rows, which does not change a
run sequence. The *observed fields* are the 3rd to 6th complete fields after the
enable marker. The 1st field can start mid-list from the strobe, and the 2nd
contains the first restart.

**Address placement.** The program, its data and its stack must not occupy any
word used below. P2's addresses are part of its stimulus (they are the bit
patterns) and must not be moved. The other propositions' lists may be moved
together by an offset if they collide with the program image.

## 4. Propositions

### P1. A Copper MOVE writes its second word into the register its first word names: for COLOR00, bits 11-0 appear bit for bit as the displayed colour

**Proposition.** A MOVE whose IR1 holds $180 writes its IR2 word into COLOR00,
and IR2 bits 11-0 (RD11-RD00) appear on the video output as red 3-0, green 3-0
and blue 3-0, each bit at its own position, in every field.
Claims: `ch2-about-the-copper.c13.s2` (p.19);
`ch2-what-is-a-copper-instruction.c4.s2` (p.20);
`ch2-the-move-instruction.c1.s2`, `ch2-the-move-instruction.c7` (p.21);
`ch2-appa-copins.c8.s2` (p.274); `COP2-copins-fields-p275.c5`, `.c6`, `.c9`,
`ch2-appa-copins.c116` (p.275); the RD11-RD00 rows: on p.36
`ch2-summary-of-copper-instructions.c26`, `.c32`, `.c38`, `.c44`, `.c50`,
`.c56`, `.c62`, `.c68`, `.c74`, `.c80`, `.c86`, `.c92` and
`COP2-summary-of-copper-instructions.c26` ... `.c92` (same suffixes); on p.274
`COP2-copins-encoding.c26` ... `.c92` (same suffixes) and `ch2-appa-copins.c39`,
`.c45`, `.c51`, `.c57`, `.c63`, `.c69`, `.c75`, `.c81`, `.c87`, `.c93`, `.c99`,
`.c105`; the terms `ch2-summary-of-copper-instructions.c98`, `.c99`, `.c100`,
`.c101` (p.36). The existential part of `ch2-about-the-copper.c6.s2` (p.19).

**Stimulus.** Baseline with the video registers set. The list at $30000:

| Offset | Words | Meaning |
|---|---|---|
| +0 | $0180,$0FFF | COLOR00 ← C0 = $0FFF |
| +4 | $4001,$FF00 | WAIT line $40 |
| +8 | $0180,$0555 | COLOR00 ← P1 |
| +12 | $5001,$FF00 | WAIT line $50 |
| +16 | $0180,$0666 | COLOR00 ← P2 |
| +20 | $6001,$FF00 | WAIT line $60 |
| +24 | $0180,$0878 | COLOR00 ← P3 |
| +28 | $7001,$FF00 | WAIT line $70 |
| +32 | $0180,$0F80 | COLOR00 ← P4 |
| +36 | $8001,$FF00 | WAIT line $80 |
| +40 | $0180,$0AAA | COLOR00 ← P5 |
| +44 | $9001,$FF00 | WAIT line $90 |
| +48 | $0180,$0999 | COLOR00 ← P6 |
| +52 | $A001,$FF00 | WAIT line $A0 |
| +56 | $0180,$0787 | COLOR00 ← P7 |
| +60 | $B001,$FF00 | WAIT line $B0 |
| +64 | $0180,$007F | COLOR00 ← P8 |
| +68 | $FFFF,$FFFE | end |

Then S($30000), with no further DMA enable bits. The CPU then idles (a loop
that touches nothing above) until 7 fields have passed, and ends.

P1-P4 encode each bit k (0..11) by the 4-bit code k+1, and P5-P8 are their
12-bit complements. Every bit is therefore 1 in four patterns and 0 in four,
and no two bit positions share a code. IR2 bits 15-12 are 0, because COLORxx
bits 15-12 are "Unused" (p.46) and give no expected value (Section 2).

**Observation.** The video output in the observed fields, as run sequences
(Section 3). The Chip-memory port, for the Copper's passes in the same
interval.

**Expected.** In every observed field, the run sequence contains, consecutively
and in this order with no other non-black value between them, the colours
(F,F,F), (5,5,5), (6,6,6), (8,7,8), (F,8,0), (A,A,A), (9,9,9), (7,8,7),
(0,7,F). The run (0,7,F) is the last non-black run of the field. Before (F,F,F)
the sequence may hold at most one run, and it must be (0,7,F): this is the
previous field's last colour, which may still be visible if the restart happens
at the end of vertical blanking (Section 2, item 5).
Sources: p.21 "Bits 15 - 0 16 bits of data to be transferred (moved) to the
register destination"; p.36 and p.275 table: IR2 bit nn = RDnn; p.275 "RD =RAM
data moved by MOVE instruction at IR2 time directly from RAM to the address
given by the DA field"; p.46 Table 3-3 "Bits 11 - 8 Red, Bits 7 - 4 Green,
Bits 3 - 0 Blue"; p.46 "COLOR00 ... shows in any area on the display where
there is no other object present and is also displayed outside the defined
display window". The quantifier "Bits 15 - 0" is graded for bits 11-0 here,
each bit individually, by the eight patterns. Bits 15-12 are graded in P2.

**Preconditions.**
- (a) In each observed field, the Copper's pass starts at $30000 and reads the
  36 words of the list in address order, with the data stored above. The extra
  read at $30048 (Section 3) belongs to no pass.
- (b) No bitplane access and no sprite access appears at the port during the
  observed fields, so nothing covers the background (p.46).
- (c) Each of the nine colours appears in at least one row of each observed
  field, so every band lies in the visible part of the field.

**Contrasting cases.**
- Main: change the IR2 word at +34 from $0F80 to $0F00. The page predicts
  (F,0,0) in place of (F,8,0), so the check goes red. All preconditions still
  hold.
- (a): start with S($30004). The passes begin at $30004 and (a) goes red. The
  program still finishes.
- (b): write all eight sprite pointers (SPRxPTH/SPRxPTL at $DFF120 + 4x, by
  MOVE.L) ← $4E000, the start of a zeroed region of 16 words, and enable sprite
  DMA (DMACON ← $8020). Sprite accesses appear and (b) goes red. Every word the
  sprites fetch is zero, so no sprite pixel is drawn and the video is
  unchanged.
- (c): change the WAIT at +20 from $6001 to $5001. The (6,6,6) band then has no
  line and (c) goes red.

**Reference frame.** Rows and fields are delimited by the sync pulses the test
observes. The check uses only the order of the bands, anchored on (F,F,F),
which the list's first MOVE sets at every restart. It needs no absolute line
number. Precondition (c) checks that all bands fall inside the visible field.

### P2. IR2 bits 15-1 reach COP1LCL bits 15-1 and IR2 bits 2-0 reach COP1LCH bits 2-0; shown by the address where the Copper restarts

**Proposition.** A MOVE to COP1LCL ($082) or COP1LCH ($080) stores IR2 bit for
bit, and the Copper restarts at the next vertical blank at the address those
bits form. This covers RD15-RD12, which COLOR00 cannot show, and checks RD11-RD00
a second time.
Claims: the RD15-RD12 rows `ch2-summary-of-copper-instructions.c2`, `.c8`,
`.c14`, `.c20` and `COP2-summary-of-copper-instructions.c2`, `.c8`, `.c14`,
`.c20` (p.36), `COP2-copins-encoding.c2`, `.c8`, `.c14`, `.c20` and
`ch2-appa-copins.c15`, `.c21`, `.c27`, `.c33` (p.274); the RD11-RD00 rows listed
under P1, a second time; `ch2-the-move-instruction.c7` (p.21);
`ch2-appa-location-registers.c2.s2`, `.c7.s2` (p.273), `ch2-appb-table.c16.s2`,
`.c22.s2` (p.290) and `ch2-appc-ecs.c3.s2` (p.309), write half only.
Supporting pages: p.26 "The Copper can write its own location registers and
strobe addresses"; p.25 "About Copper restart"; p.32 "You can change the value
in the location registers at any time ... restored to the Copper's program
counter at the start of the vertical blanking period".

**Stimulus.** Baseline. Twelve segments, each three instructions (12 bytes) at
address T: `$0082,Lnext`, `$0080,Hnext`, `$FFFF,$FFFE`. The CPU starts the
first one with S($34000) and then idles for 15 fields.

|---|---|---|---|
| 0 | $34000 | $AAAA, $0001 | $1AAAA |
| 1 | $1AAAA | $CCCC, $0001 | $1CCCC |
| 2 | $1CCCC | $F0F0, $0001 | $1F0F0 |
| 3 | $1F0F0 | $FF00, $0001 | $1FF00 |
| 4 | $1FF00 | $5554, $0001 | $15554 |
| 5 | $15554 | $3332, $0001 | $13332 |
| 6 | $13332 | $0F0E, $0001 | $10F0E |
| 7 | $10F0E | $00FE, $0001 | $100FE |
| 8 | $100FE | $2000, $0005 | $52000 |
| 9 | $52000 | $2000, $0006 | $62000 |
| 10 | $62000 | $2000, $0002 | $22000 |
| 11 | $22000 | $2000, $0001 | $12000 |
| 12 | $12000 | $2000, $0001 | $12000 (itself) |

The L values $AAAA, $CCCC, $F0F0 and $FF00 give each bit k (1..15) the 4-bit
code k, and $5554, $3332, $0F0E and $00FE are their complements within bits
15-1. The H values $0005 and $0006 give bits 0, 1 and 2 distinct codes, and
$0002 and $0001 are their complements within bits 2-0. Bit 0 of L is always 0
(word addresses; p.287 "+ ... Must be an even address"). H bits 15-3 are always
0 (Section 2, item 4).

**Observation.** Copper accesses at the port from the enable marker until 14
restart accesses have occurred.

### P3. The word a MOVE delivers is the content of RAM at its IR2 fetch

**Proposition.** When the program changes the IR2 word of a MOVE in RAM between
two passes, the next pass moves the new word. In every pass the moved value is
the word the Copper read from RAM at the IR2 access.
Claims: `COP2-copins-fields-p275.c7`, `.c8`, `ch2-appa-copins.c115`, `.c116`
(p.275); `ch2-the-move-instruction.c1.s2` (p.21, "transfers data from RAM").

**Stimulus.** Baseline with the video registers set. The list at $36000:
`$0180,$0FFF` (+0), `$8001,$FF00` (+4), `$0180,$0F0F` (+8, so the IR2 word is at
$3600A), `$FFFF,$FFFE` (+12). A spare word $0000 sits at $36010. Then S($36000).
Starting with the 3rd field after the enable marker, for each value $00FF,
$0FF0, $0A5A and $05A5 in turn, the CPU:
1. waits until VPOSR bit 0 = 0 and VHPOSR bits 15-8 = $A0 (line $A0, p.285);
2. writes the value to $3600A with MOVE.W;
3. waits until VHPOSR bits 15-8 ≠ $A0.

This is one change per field, made after line $80's MOVE and before the next
field's.

**Observation.** At the port: every Copper read of $3600A (time r_j, data d_j)
and every CPU write to $3600A. On the video: from the 3rd field after the
enable marker until 2 fields after the last CPU write, the *band rows*. These
are the rows that come after the (F,F,F) run of a field and whose sample is
non-black and not (F,F,F).

**Expected.**
- (i) Each d_j equals the last value the CPU wrote to $3600A before r_j, or
  $0F0F before the first write.
- (ii) The colour of every band row equals the low 12 bits of d_j, where r_j is
  the latest Copper read of $3600A before that row's sample time.
- (iii) Over the observed passes, the values moved are $0F0F, $00FF, $0FF0,
  $0A5A, $05A5, in this order. Each one is moved from the first pass after its
  CPU write until the next write.

Graded for every pass and every band row in the interval.
Source: p.275 "RD =RAM data moved by MOVE instruction at IR2 time directly from
RAM to the address given by the DA field".

**Preconditions.**
- (a) Between two consecutive Copper reads of $3600A there is at most one of
  the program's four value writes, and every value write is followed by at
  least one Copper read of $3600A. Each value thus has at least one pass of its
  own.
- (b) Every pass contains a Copper read of $3600A, so the IR2 word is fetched
  from RAM in each pass.

**Contrasting cases.**
- Main: the CPU writes the four values to $36010 instead of $3600A, still one
  per field. The page predicts that $0F0F is moved in every pass, so (iii) goes
  red. Preconditions (a) and (b) still hold.
- (a): the CPU writes all four values within one field, with no wait. Several
  value writes then fall between the same two reads, and (a) goes red.
- (b): replace the WAIT at +4 by `$FFFF,$FFFE`. The Copper stops there and never
  reads $3600A, so (b) goes red. The CPU's writes to $3600A are then never read
  and do no harm.

**Reference frame.** Band rows are tied to passes by time: the latest Copper
read of $3600A before the row's sample. The MOVE runs at the start of line $80
and the row sample lies in the middle of a line at or after $80, so the read
always precedes the rows it governs. No absolute line anchor is needed.

### P7. With COPCON bit 1 (CDANG) set, a Copper MOVE writes a register in $40-$7E: a MOVE to BLTSIZE starts the blitter

**Expected.** Exactly one blitter write occurs in the interval. It is at $48000,

## 6. Attribution

This section replaces the paragraph "Access attribution" of Section 3, and
every use of "Copper access", "blitter access", "audio channel 0 access",
"sprite access", "bitplane access" and "CPU access" in Sections 3 and 4 reads
as defined here.

The harness's RAM-port record carries no requester. A record has a cycle, an
address, a data word, a direction and byte lanes (`RamAccess`), so no access
is attributed by a channel field. An access is attributed by construction:

- Each channel under test reads from its own region of Chip memory, and a
  Copper list, a blitter destination, an audio data block and a marker word
  each have an address range no other channel and no CPU instruction uses. An
  access at the port inside a channel's region is that channel's access.
- The DMA channels the proposition does not test are off (DMACON), and the
  channels that stay off have their pointer registers set into regions of
  their own, so that an access of an off channel could not be mistaken for an
  access of the channel under test.
- A precondition shows from the assembler listing (`vasm -L`, 68000 mode, as
  `integration/ch1-cpu-system`'s P3.c helper does) that the CPU program
  executes no data access to any such region inside the measurement window,
  on any effective-address path: absolute, PC-relative, or through an address
  register whose value the listing's instructions set. A proposition whose
  stimulus has the CPU write a region on purpose (P3, P5, P7) names that
  write as the only allowed access to that word, and the precondition allows
  that write alone.

A proposition whose observation cannot be attributed this way is declined to a
RECORDED line that gives this as the reason.

## 8. Lead amendments

Four rules added after the first run of the rebuilt package. Where one of them
differs from the text of Sections 2 to 5, the rule prevails, and those sections
have been changed to agree with it. Each rule gives its reason.

**A1. The read after an end WAIT.** No page says whether the Copper fetches the
word after a WAIT's second word before it waits or restarts. A Copper read at
the word following an end WAIT's second word ($FFFE), before the next restart,
is the *extra read*. It is printed as a MEASURED line and belongs to no pass.
The restart access is the first Copper access after the end WAIT's second word
that is not the extra read. P1 (a) and
every pass definition follow this rule (Section 3; P1 (a); P2 (b); P3 (b);
P4 (a), (b); P5 (c); P7 (c)).
Reason: the first run read the word after the end WAIT in every pass on both
cores, 16 cycles before the restart read. Taking the first access after the
$FFFE read as the restart access graded a question the pages leave open, and
turned the preconditions of P1, P2, P4, P5 and P7 red for it.

**A2. A MOVE behind a WAIT that is never satisfied (P4 (ii)).** The pages say
such a MOVE does not run. They say nothing about fetching it. P4 (ii) grades
that MOVE's effect, the value of its target register (COLOR00) at the field
boundary, read as this specification reads registers (the run sequence of
Section 3), and prints the Copper's reads of its words as MEASURED.
Reason: "no Copper read of $38010 or $38012" graded fetching, and the extra
read of A1 is a read of $38010.

**A3. P5 (a): the boundary is marker 2.** The Copper starts as soon as Copper
DMA is on. The boundary for "no Copper access before DMA is enabled" is
therefore the marker written before the DMACON write (marker 2 in the P5 runs),
not the enable marker written after it. The windows of P5 that began at marker 3
begin at marker 2, and P4 observes from marker 0 because the Copper's first
reads precede the enable marker.
Reason: the Copper's first two list words are read about 60 clk_sys cycles
before the enable marker is written, so (a) with marker 3 was red for any
stimulus that follows S(T).

**A4. P8: the first audio run is graded.** With AUD0LEN = 4 the first run after
marker 2 is graded like every other run. The earlier sentence that the first
run is not graded is removed, and so is the entry for it in Section 2. P8-CTRL
keeps grading the runs after the first, by the same comparator. In the
recorded run the cores read three words before the first restart (red; the
mechanism of NM-HRM-084).
Reason: the pages do not say the first run is shorter. p.164: "The length counter counts down once with each word that comes in"; the first data word, which "must be thrown away", is a word that comes in, so with p.145 step 4 (AUDxLEN is "the number of data words to be retrieved before starting at the address currently in AUDxLC") the first run also has AUD0LEN fetches.
