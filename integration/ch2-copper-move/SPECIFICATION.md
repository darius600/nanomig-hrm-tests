# Copper MOVE and location registers: integration test specification

This document specifies one integration test package for an FPGA
re-implementation of the Amiga chip set: the Copper MOVE instruction, the
Copper location registers it and the 680x0 load, and the automatic restart of
pointers from location registers. The author wrote it from the package's
claims (`claims-spec-stage.jsonl`) and the pages of the *Amiga Hardware
Reference Manual*, 3rd edition, and never saw the implementation or any test.
Page numbers are printed page numbers. Hex values carry the manual's `$`
prefix. Addresses are byte addresses unless called word addresses (word
address = byte address / 2).

Seven propositions follow (P1 to P7). Section 1 lists the claims that became
no proposition, section 2 the claims that were used only in part, section 3
what the pages leave open or disagree on, and section 4 the setup and
instruments that all propositions share. Section 6 maps every claim to where
it is used.

## 3. What the pages leave open or disagree on

### 3.1 Which registers the Copper may write

- p.21: "Any register whose address is $20 or above." / "Any register whose
  address is between $10 and $20 if the Copper danger bit is a 1." / "The
  Copper cannot write into any register whose address is lower than $10."
- p.26: "The registers that the Copper can always affect are numbered $80
  through $FF inclusive. ... Those it cannot affect at all are numbered $00 to
  $3E inclusive. ... The rest of the registers, from $40 to $7E, are protected
  by a bit in the Copper control register." ... "When CDANG is 0, these
  registers cannot be written by the Copper."
- p.287 (Appendix B legend): "`*` Address not writable by the Copper." / "`~`
  Address not writable by the Copper unless the "copper danger bit", COPCON is
  set true." On pp.289-293 the `*` covers $000-$03E and the `~` covers
  $040-$07E. No row from $080 on carries either mark, including $100-$1FE,
  which p.26's "$80 through $FF" does not mention.
- p.310 (ECS): "In the standard chip set, if this is set, the Copper can access
  the address range from $DFF03E through $DFF07E. Now, in the ECS, if this bit
  is set, the Copper can access all of the Amiga chip registers. If this bit is
  clear, the Copper can access the address range from $DFF03E through
  $DFF07E".

All pages agree on one thing only: the Copper can always write the registers
at $080-$0FE, whatever CDANG holds. Every register this package writes with a
Copper MOVE lies in that range: COP2LCH $084, COP2LCL $086, COPJMP2 $08A,
INTENA $09A, and INTREQ $09C in one contrasting case. The program also writes
COPCON = $0000 at the start (p.26: "the CDANG bit is cleared after a reset").
That state is irrelevant for these addresses on every page.

### 3.2 Width and contents of the location registers

- p.25: "COP1LCH High 3 bits of first Copper list address. COP1LCL Low 16 bits
  of first Copper list address." Later on the same page: the lower-addressed
  register "contains the most significant data, or high 3 bits of the address",
  and the higher-addressed one "the least significant data, or low 15 bits of
  the address. Therefore, you write the 18-bit address by moving one long word
  to the register whose name ends in "H.""
- p.273 and p.290: "(high 3 bits, high 5 bits if ECS)" and "(low 15 bits)".
  p.309: "COP1LCH ... (high 5 bits,was 3 bits)". p.276: "18-bit pointer
  registers".

This package uses only bits 15-1 of the L word (p.25's list gives 16 bits
against its own text and p.273, so bit 0 is never set). It also uses bits 2-0
of the H word, which all pages give. Bits 4-3 of the H word (address bits
A20-A19) rest only on the ECS pages (pp.273, 290, 309). p.25 gives 3 bits
without naming a chip set. Checks on those two bits run with ECS selected and
are reported as a separate verdict, so that a reader who takes p.25 as binding
for ECS can set them aside.

### 3.3 When the Copper restarts from COP1LC

- p.25: "At the start of each vertical blanking interval, COP1LC is
  automatically used to start the program counter. That is, no matter what the
  Copper is doing, when the end of vertical blanking occurs, the Copper is
  automatically forced to restart its operations at the address contained in
  COP1LC." The paragraph gives both start and end.
- p.276: "at the beginning of each vertical blank time". p.30: "When the screen
  display ends and vertical blanking starts, the Copper will automatically be
  pointed to the top of its instruction list". p.32: "at the start of the
  vertical blanking period". p.288: "(during vertical blank)".
- Where vertical blanking ends: p.219: "The range starts at line 0 and ends at
  line 20 for NTSC or line 25 for PAL." p.79 (table): "Vertical Blank Start 0
  0 / Vertical Blank Stop $15 (21) $1D (29)".

All pages agree that the restart happens once per field, within vertical
blanking, and that vertical blanking begins at line 0. P6 therefore checks for
exactly one restart per field and for a restart no earlier than the beam's wrap
to line 0 and no later than line $1D (PAL) or $15 (NTSC). The test goes red
only where every page puts the restart outside vertical blanking. It reports
the measured line so that the start/end question stays visible.

### 3.4 Strobe by read or by write

p.30's start sequence strobes with a read ("MOVE.W COPJMP1(a1),d0 ; Causes
copper to load PC from COP1LC"). p.26 ("When you write to a Copper strobe
address"), p.276 ("whenever strobe addresses COPJMP1 or COPJMP2 are written")
and p.287 ("S Strobe ... Writing the register causes the effect") describe a
write. Every program in this package strobes with a word **write**, on which
all pages agree. The package asserts nothing about a read.

### 3.5 Where the Appendix A instruction table is printed

The claims `COP2-copins-encoding.*` and `ch2-appa-copins.c15 ... c105` cite
p.274. In the printed book, p.274 holds only the COPCON entry, the start of the
COPINS entry and the one-line summaries of MOVE, WAIT and SKIP. The bit table
and its legend are printed on **p.275**, headed "COPINS (cont.)". The rendered
page was checked row by row: every MOVE IR1 and IR2 cell reads as the page text
gives it (X ... X, DA8-DA1, 0; RD15-RD00). So the "differing between editions"
remarks in some of those claims do not reflect a different MOVE column in the
print. The same holds for Table 2-2 on p.36.

### 3.6 Audio: the first block and the restart request

- p.164: "Because of pipelining in Agnus, the first data word must be thrown
  away." ... "When it finishes, a DMA restart request goes to Agnus along with
  the regular DMA request. This tells Agnus to reset the pointer to the
  beginning of the table of data."
- p.145: "Set the length register, AUDxLEN, to the number of data words to be
  retrieved before starting at the address currently in AUDxLC." p.139: "Each
  time the system retrieves the last audio word from the data area, it uses the
  contents of these location registers to again find the start of the data."
  p.147: "Each time the length counter reaches zero, both the location and
  length registers are reloaded".
- p.145: "Enabling an audio channel almost always starts the data output again
  from the top".

p.164 leaves open the exact fetch sequence of the first block after the
channel is enabled. P7 therefore makes no assertion about the first block and
checks every block end after it, where the pages agree.

### 3.7 Smaller points

- p.35, Table 2-1 names INTREQ bit 4 "COPEN". p.280 names it "COPER", and
  COPEN is DMACON bit 7 (p.30, p.278). This package uses INTENA bit 4 only as a
  data bit, so the name does not matter.
- p.218: "bit 15 has no meaning in the read-only addresses". INTENAR bit 15 is
  therefore masked everywhere.

## 4. Common setup

### 4.1 Configuration

- Enhanced Chip Set selected, PAL, 2 MB Chip memory, for every run. P6 is also
  run with NTSC selected.
- Every run is executed once on each of the two CPU cores, and both must pass
  with identical expectations.
- A "run" is one program execution with its capture. A "field" is the span
  between two successive wraps of the beam line counter to 0 (4.4, I2).

### 4.2 Memory map

The program, its vectors and its stack may go anywhere except the reserved
areas below.

| Area | Use |
|---|---|
| $0C0000-$0CFFFF | P1-B/P5 targets, set S_L1 (defined in P1), plus the P1 contrasting-case park at $0C0060 |
| $0D0000-$0DFFFF | P1-B/P5 targets, set S_L0 |
| $01F000, $02F000, $04F000, $08F000, $10F000 (16 bytes each) | P1-B/P5 targets, set S_H1 |
| $1EF000, $1DF000, $1BF000, $17F000, $0FF000 (16 bytes each) | P1-B/P5 targets, set S_H0 |
| $10000E-$100011 | P5 contrasting-case park |
| $0E0000-$0E0203 | list L_A (P1-A, P2) |
| $0E1000-$0E1013 | list L_B (P1-B) |
| $0E2000-$0E200F | list L_3 (P3) |
| $0E3000, $0E3100, $0E3200 (4 bytes each) | lists L6a, L6b, L6c (P6) |
| $0E4000-$0E400F, $0E4100-$0E410F | audio buffers A and B, each 4 words followed by 4 guard words (P7) |
| $0E6000-$0E607F | P4 scratch |
| $0E7000-$0E71FF | markers and CPU-stored readbacks |
| $0E8000-$0E8003 | decoy park D |
| $0E9010-$0E9013 | P5 word-write target park |
| $110000-$13FFFF | monitor log buffer (I2) |

A *park* is the two words `$FFFF,$FFFE`, the WAIT for VP=$FF, HP=$FE that
p.23 and p.30 describe as never satisfied.

**Copper regions** are all the areas above except the audio buffers, the P4
scratch, the markers and the log buffer. **Audio regions** are the two audio
buffers with their guard words.

### 4.3 Program frame

Every program performs these steps, in this order:

1. SR = $2700 (no 680x0 interrupt is taken. p.217: levels 1-6 are the only
   ones generated).
2. INTENA ← $7FFF, INTREQ ← $7FFF, DMACON ← $7FFF, ADKCON ← $7FFF (clear all,
   using the SET/CLR rule of p.218, p.278 and p.265), and COPCON ← $0000.
3. Write every list, pad, park and buffer the run needs, as specified. These
   CPU writes appear at the port and are the reference for G4.
4. Run-specific register setup, such as the decoy in COP2LC.
5. For runs that use the Copper (p.30: initialize a location register "and
   write to its strobe address before Copper DMA is turned on"):
   `MOVE.L #L,$DFF080` (COP1LCH), then a word write to $DFF088 (COPJMP1),
   then marker M0, then `MOVE.W #$8280,$DFF096` (DMACON: SET/CLR, DMAEN,
   COPEN; p.278). Then read DMACONR ($DFF002) and store it at $0E7100.
   Bitplane DMA stays off. Only the Copper is enabled. p.30's example also
   enables raster DMA, but p.30 prescribes the order, not the raster.
6. The run's own part (monitor loop or steps).
7. A final marker, after which the program idles in a loop in its own code
   region. The harness ends the capture after the number of fields the run
   names.

### 4.4 Instruments and reference frames

**I1: Copper instruction fetches.** A *Copper read* is a read at the port whose
address lies in a Copper region. This identification holds because the CPU
program never reads a Copper region, no DMA channel other than the Copper and
refresh is enabled in a Copper run, and G1 shows that no read lands there while
Copper DMA is off. An *instruction fetch at X* is a Copper read at X followed,
as the next Copper read, by a read at X+2. p.20: "All Copper instructions
consist of two 16-bit words in sequential memory locations. Each time the
Copper fetches an instruction, it fetches both words." Its first read is IR1
and its second read is IR2 (p.36: "IR1 = first instruction word / IR2 = second
instruction word"). A Copper read that belongs to no pair is recorded and
reported but is not an instruction fetch. t1(x) and t2(x) denote the port
times of the IR1 and IR2 reads of fetch x.

**I2: monitor loop.** Runs P1-A, P1-B, P2, P3 and P6 end their program in a
loop that reads INTENAR ($DFF01C), VPOSR ($DFF004) and VHPOSR ($DFF006), in
that order, and stores each value as the next word of the log buffer. The
builder chooses the instructions, for example three
`MOVE.W custom(A5),(A1)+` and a bounds check. A *sample* is one such triple.
Its time *s* is the port time of the INTENAR store. Its beam reading is the
line V = 256 x (VPOSR bit 0) + (VHPOSR bits 15-8) and the horizontal count
H = VHPOSR bits 7-0 (p.285: "V7 ... V0,H8 ... H1"; VPOSR bit 0 is "V8").
The loop's order yields two facts:

- The INTENAR value of a sample was read **before** *s*, because a read
  precedes the store of its value.
- The beam values of a sample were read **after** *s*, in program order.

Samples whose V differs by more than 1 from both neighbours are discarded as
torn reads at the V8 boundary. A *wrap* is a point where V falls by more than
200 between consecutive kept samples. A *field* runs from one wrap to the
next.

**I3: markers.** A marker is a CPU word write to the next word at $0E7000+.
The value written is the VHPOSR value the CPU read immediately before, so each
marker carries a beam reading. Markers bracket CPU register writes, which the
port cannot see.

**I4: time unit.** One memory cycle is one horizontal count (p.24: "One
horizontal count takes one cycle of the system clock"). That is 280 ns
(p.275: "memory cycles are 280 ns"; p.285: "RESOLUTION = 1/160 of screen width
(280 ns)"). The builder converts port time to memory cycles with the ratio
that makes the H field of the I2 samples advance by one per memory cycle
within a line, and asserts that the ratio is constant over the capture.
**M = 32 memory cycles** is the margin used below.

### 4.5 Common preconditions

A check passes only if every one of its preconditions holds. A failed
precondition fails the check with the reason "precondition", never with a
pass. Every contrasting case below is a run of its own. In it, "prescribed"
(G4) means the words of that contrasting case, and all other preconditions
still hold unless the contrast is aimed at them.

| Id | Precondition | How the test asserts it | Contrasting stimulus | Predicted result |
|---|---|---|---|---|
| G1 | Copper reads are identifiable | A baseline run of the same program writes DMACON $8200 (no COPEN) instead of $8280. It shows no read in any Copper region over the same capture. | In the baseline, the CPU program also executes one `MOVE.W $0E1000,D0` | G1 red: one read in a Copper region |
| G2 | Copper DMA is on | The DMACONR value stored at $0E7100 has bits 9 and 7 set (p.278: "09 DMAEN", "07 COPEN") | DMACON written $8200 | Bit 7 reads 0 and G2 goes red (no Copper reads either) |
| G3 | The list starts where it was put | The first Copper instruction fetch after marker M0 is at L (p.25: "the corresponding location register is loaded into the Copper program counter ... from which its next instruction will be fetched"; p.30) | COP1LCH is written with D instead of L | First fetch at D, G3 red |
| G4 | The words the Copper reads are the specified words | The data of every Copper read equals the word this specification prescribes for that address, as the setup writes at the port show. For a contrasting case (or a precondition's own mutation), "prescribed" means that run's own words -- whatever its own setup actually wrote -- not the main run's; a check's own dedicated mutation, which deliberately writes a word this specification does not prescribe, is the one exception, and is graded against the main run's words so that the divergence is what turns it red. | Step 3 writes one list word differently (for example the IR2 of L_A half-step b0 as $8002) | G4 red at that address |

| G6 | Enough samples | Every interval that a check counts holds at least 5 kept samples | The monitor loop has a delay of about 2 lines added per iteration | G6 red |

## 5. Propositions

### P1. A MOVE writes its second word, bit for bit, into the register its first word addresses

**1. Proposition.** A Copper MOVE writes the 16 bits of its second
instruction word (IR2 = RD15 ... RD00), unchanged and bit n to bit n, into the
register whose address is in its first instruction word (DA8 ... DA1).

Claims:

- `ch2-about-the-copper.c13.s2` (p.19)
- `ch2-about-the-copper.c6.s2` (p.19, in part, section 2)
- `ch2-what-is-a-copper-instruction.c4.s2` (p.20)
- `ch2-the-move-instruction.c1.s2`, `ch2-the-move-instruction.c7` (p.21)
- Table 2-2 rows (p.36): `ch2-summary-of-copper-instructions.c2, c8, c14, c20, c26, c32, c38, c44, c50, c56, c62, c68, c74, c80, c86, c92`
- Table 2-2 rows (p.36): `COP2-summary-of-copper-instructions.c2, c8, c14, c20, c26, c32, c38, c44, c50, c56, c62, c68, c74, c80, c86, c92`
- Appendix A table rows (cited p.274, printed p.275, 3.5): `COP2-copins-encoding.c2, c8, c14, c20, c26, c32, c38, c44, c50, c56, c62, c68, c74, c80, c86, c92`
- Appendix A table rows (cited p.274, printed p.275, 3.5): `ch2-appa-copins.c15, c21, c27, c33, c39, c45, c51, c57, c63, c69, c75, c81, c87, c93, c99, c105`
- `ch2-appa-copins.c8.s2` (p.274)
- `COP2-copins-fields-p275.c5, c6, c9`, `ch2-appa-copins.c116` (p.275)
- Table 2-2 legend (p.36): `ch2-summary-of-copper-instructions.c98, c99, c100, c101`

Two instruments observe the register contents: **A**, INTENA read back
through INTENAR by the CPU, and **B**, COP2LC read back through the address the
Copper jumps to. Every register lies in $080-$0FE (3.1).

**2. Stimulus.**

*Run P1-A-set* (3 fields captured, monitor loop running). List L_A at $0E0000,
started by the program frame with L = $0E0000. The list has 64 half-steps,
two per value P_i (i = 0 ... 31), and then a park:

- half-step a_i: WAIT line v = $30 + 4i, then MOVE `$009A,$7FFF`
- half-step b_i: WAIT line v + 2, then MOVE `$009A,$8000|P_i`

A WAIT for line v is the two words `(v<<8)|$01, $FF00`. This is the form p.23
gives ("DC.W $9601,$FF00 ;Wait for line 150, ignore horizontal counters"):
IR1 bit 0 = 1, IR2 bit 15 (BFD) = 1, VE all 1 and HE all 0 (p.22). A MOVE is
`IR1 = register address` (bits 15-9 = 0, bit 0 = 0) and `IR2 = data` (p.21:
"Bit 0 Always set to 0", "Bits 8 - 1 Register destination address", "Bits
15 - 9 Not used, but should be set to 0"; p.21 example "DC.W $00E0,$0002").
Each half-step takes 8 bytes (WAIT, then MOVE), so half-step a_i starts at
$0E0000 + 16i and b_i at $0E0008 + 16i. The 64 half-steps end at $0E01FF and
the final park is at $0E0200.

The values P_i are:

| i | P_i | i | P_i |
|---|---|---|---|
| 0-14 | $0001, $0002, $0004, $0008, $0010, $0020, $0040, $0080, $0100, $0200, $0400, $0800, $1000, $2000, $4000 (walking one, bit i) | 15-29 | $7FFE, $7FFD, $7FFB, $7FF7, $7FEF, $7FDF, $7FBF, $7F7F, $7EFF, $7DFF, $7BFF, $77FF, $6FFF, $5FFF, $3FFF (walking zero, bit i-15) |
| 30 | $0000 | 31 | $7FFF |

*Run P1-A-clear*: the same list, except that the MOVE of a_i is `$009A,$FFFF`
and the MOVE of b_i is `$009A,P_i` (bit 15 = 0).

Before step 5 of the frame, the CPU tests the instrument itself (P1-p2):
INTENA ← $7FFF, read INTENAR; INTENA ← $D555, read; INTENA ← $7FFF, read. The
three values are stored at $0E7102, $0E7104 and $0E7106.

*Run P1-B* (3 fields captured, monitor loop running). The CPU writes
`MOVE.L #$000E8000,$DFF084` before step 5, which puts the decoy D in COP2LC.
List L_B at $0E1000, started with L = $0E1000:

```
$0E1000  $4001,$FF00      WAIT line $40
$0E1004  $0084,H(T[1])    MOVE COP2LCH
$0E1008  $0086,L(T[1])    MOVE COP2LCL
$0E100C  $008A,$0000      MOVE COPJMP2 (strobe)
$0E1010  $FFFF,$FFFE      park
```

Here H(T) = T >> 16 and L(T) = T & $FFFF. The 40 targets T[1] ... T[40] are
the sets below, in this order: S_L1, then S_L0, then S_H1, then S_H0.

- **S_L1** (H = $000C; one bit of L set alone, bits 1-4 on a background of
  high bits so that the pads do not overlap): $0C0020, $0C0040, $0C0080,
  $0C0100, $0C0200, $0C0400, $0C0800, $0C1000, $0C2000, $0C4000, $0C8000
  (bits 5-15), $0C5002, $0C6004, $0CA008, $0CC010 (bits 1, 2, 3, 4).
- **S_L0** (H = $000D; one bit of L cleared alone): $0DFFDE, $0DFFBE, $0DFF7E,
  $0DFEFE, $0DFDFE, $0DFBFE, $0DF7FE, $0DEFFE, $0DDFFE, $0DBFFE, $0D7FFE
  (bits 5-15), $0DAFFC, $0D9FFA, $0D5FF6, $0D3FEE (bits 1, 2, 3, 4).
- **S_H1** (L = $F000; one H bit set): $01F000, $02F000, $04F000, $08F000,
  $10F000.
- **S_H0** (L = $F000; one H bit cleared out of 5): $1EF000, $1DF000,
  $1BF000, $17F000, $0FF000.

At each T[k] (k = 1 ... 39) there is a 16-byte pad:
`$0084,H(T[k+1])` at T[k], `$0086,L(T[k+1])` at T[k]+4, `$008A,$0000` at
T[k]+8, and the park `$FFFF,$FFFE` at T[k]+12. At T[40] there is only a
park. H words have bits 15-5 = 0 and L words have bit 0 = 0 (3.2). p.26
describes this use: "you might MOVE an indirect address into the COP2LC
location register. Then, any MOVE instruction that addresses COPJMP2 strobes
this indirect address into the program counter."

**3. Observation.**

*A:* the I2 samples. The hold interval of half-step h is the set of samples
with *s* in (t2(h) + M, t2(h+1)]. Here t2(h) is the IR2 read of h's MOVE and
h+1 is the next half-step. For the last half-step, h+1 is half-step a_0 of the
next field. Every field of the capture counts. Samples stored no later than
t2(h+1) were read before the next MOVE's data reached the chip, so the state
of h is the only state they can show.

*B:* the I1 instruction fetches. For each field and k = 0 ... 39, let J_k be
the instruction fetch of the MOVE COPJMP2 that sends the Copper to T[k+1], and
let Z_k be the park that follows it. For k = 0 (list L_B), J_0 is at $0E100C
and Z_0 at $0E1010. For k >= 1 (pad T[k]), J_k is at T[k]+8 and Z_k at
T[k]+12. The observation interval runs from t2(J_k) to the next wrap.

**4. Expected value.**

*A:* in every hold interval, (INTENAR AND $7FFF) equals:

| Run | after a_i | after b_i |
|---|---|---|
| set | $0000 | P_i |
| clear | $7FFF | $7FFF AND NOT P_i |

Sources: p.21: "Bits 15 - 0 16 bits of data to be transferred (moved) to the
register destination". p.218: "When you wish to set a bit (make it a 1), you
must place a 1 in the position you want to set and a 1 into position 15. When
you wish to clear a bit ... place a 1 in the position you wish to clear and a
0 into position 15." p.280: "Bits written with a zero are always unchanged."
p.217: "INTENAR ... Reads contents of INTENA." p.218: bit 15 "has no meaning
in the read-only addresses", hence the mask.

*B:* the next instruction fetch after J_k is at T[k+1] = ((H AND $001F) << 16)
OR L. Here H and L are the IR2 data of the two MOVEs to $084 and $086 that
precede J_k, as read at the port. No instruction fetch at Z_k occurs in the
field. A single unpaired read at Z_k is allowed and reported, because no page
says whether the Copper may read the next word before the jump takes effect.
The chain must reach T[40] in every field. Sources: p.26 (quoted
above); p.25: the lower-addressed register "contains the most significant
data" and the higher-addressed one "the least significant data"; pp.273, 290
and 309 for the widths (3.2); p.25: "This causes the Copper to jump to a new
location, from which its next instruction will be fetched."

*Quantifier "16 bits ... bit n carries RDn" (every n).* Each IR2 bit is shown
as a walking one (the only 1 among its neighbours) and as a walking zero (the
only 0), in its own position. In B, the L values for bits 1-4 also carry two
high bits as background (S_L1, S_L0), so that the pads do not overlap. The
values for bits 5-15 carry none.

| IR2 bit | Walking one | Walking zero |
|---|---|---|
| 0 | A: b_0 (set run); B: S_H1 $01F000 | A: b_15 (set run); B: S_H0 $1EF000 |
| 1-4 | A: b_1-b_4; B: S_L1 bits 1-4 and S_H1 | A: b_16-b_19; B: S_L0 bits 1-4 and S_H0 |
| 5-14 | A: b_5-b_14; B: S_L1 | A: b_20-b_29; B: S_L0 |
| 15 | A: every b_i of the set run (bit 15 = 1 sets); B: $0C8000 | A: every b_i of the clear run (bit 15 = 0 clears); B: $0D7FFE |

B's verdict is reported in three parts: L bits 15-1, H bits 2-0, and H bits
4-3 (ECS pages only, 3.2). The quantifier "most of the chip control registers"
is not graded (section 2).

**5. Preconditions.** Runs P1-A-set and P1-A-clear: G1-G6. Run P1-B: G1-G4
(it runs the monitor loop but uses no samples). In addition:

| Id | Precondition | Contrasting stimulus | Predicted result |
|---|---|---|---|
| P1-p1 | In every field, every half-step's WAIT and MOVE instruction fetches (A), or every pad's three MOVE fetches (B), are present, in list order | Half-step a_5's WAIT is replaced by a park ($FFFF,$FFFE) | Half-steps from a_5 on are never fetched, so P1-p1 goes red. The program still finishes. |
| P1-p2 | The instrument works: the CPU's own INTENA writes read back as $0000, $5555 and $0000 (masked) | The $D555 write is omitted | Second value $0000, P1-p2 red |
| P1-p3 | In B, COP2LC holds the decoy D when the chain starts, so a landing at T[1] cannot come from a stale COP2LC. Asserted by a *calibration run*: L_B with its two MOVEs to $084/$086 replaced by `$009A,$0000` (no effect: p.280, bits written with zero are unchanged). The first fetch after J_0 must be at D ($0E8000). | In the calibration run the CPU writes COP2LC = $000E9010 (the P5 park) instead of D | The first fetch after J_0 is at $0E9010, so P1-p3 goes red |

**6. Contrasting cases.**

- C1 (DA): in run P1-A-set, the IR1 word of b_0's MOVE is $009C (INTREQ)
  instead of $009A. Prediction: INTENA is not written by b_0. Its hold
  interval shows $0000, not $0001. INTREQ receives the write, which is not
  checked. All other half-steps stay as expected.
- C2 (one data bit): in run P1-A-set, b_0's IR2 is $8002. Prediction: the hold
  interval shows $0002.
- C3 (B, one L bit): pad T[1] ($0C0020) moves L = $0060 instead of $0040, and
  a park sits at $0C0060. Prediction: the jump lands at $0C0060, and T[2] ...
  T[40] are not visited in that field.

**7. Reference frames.** Copper fetches follow I1 and are anchored by G3 (the
list starts at L) and by P1-p1 (list order). Hold intervals are anchored on
the IR2 reads of the list's own MOVEs, the time of the move according to P2.
Margins are in memory cycles (I4).

### P2. The written data is the word read from RAM as the instruction's second word, at each execution

**1. Proposition.** At every execution of a MOVE at address A, the value
written is the word the Copper reads from A+2 as that instruction's second
read (IR2). The word is read from RAM afresh at that execution. The
destination still holds the old value before that read and holds the new
value after it.

Claims: `COP2-copins-fields-p275.c5, c6, c7, c8`, `ch2-appa-copins.c115`,
`ch2-appa-copins.c116` (p.275); `ch2-the-move-instruction.c1.s2` (p.21);
`ch2-summary-of-copper-instructions.c98, c99` (p.36).

**2. Stimulus.** Run P1-A-set (P1) with 4 fields captured and one change.
Inside the monitor loop, after the first wrap that follows the first complete
execution of the list, the CPU writes the word $AAAA to $0E000E once. That
address holds b_0's IR2, $8001 before the change. The write is bracketed by
markers. The builder chooses the iteration count. Every other MOVE in the
list stays unchanged.

**3. Observation.** For every execution e of every MOVE in L_A over the
capture:

- r1(e) and r2(e) are the IR1 and IR2 reads (I1)
- d(e) is the data of r2(e)
- t2(e) is the time of r2(e)

The samples are those of the hold intervals of P1, plus the samples with
*s* <= t2(e) in the preceding hold interval.

**4. Expected value.** For every execution e:

- (i) r2(e) is at A+2 and immediately follows r1(e) at A as the next Copper
  read.
- (ii) For b_0, d(e) = $8001 if t2(e) precedes the CPU write of $AAAA at the
  port, and $AAAA if it follows it.
- (iii) The hold interval after e shows the state that d(e) produces
  according to P1's table. For b_0 that is $0001 before the change and $2AAA
  after it.
- (iv) The hold interval before e, which runs up to t2(e) itself, shows the
  state before e. The hold interval after e, from t2(e) + M, shows the state
  after e. So no sample read before the IR2 read sees the new value, and every
  sample stored more than M after it does.

In run P1-B, the IR2 read of each J_k lies at the J_k address + 2, fetched
from the old sequence, and precedes the first read at T[k+1]: the strobe takes
effect only once its IR2 has been read.

Sources: p.275: "RD =RAM data moved by MOVE instruction at IR2 time directly
from RAM to the address given by the DA field." p.21: "The MOVE instruction
transfers data from RAM to a register destination. The transferred data is
contained in the second word of the MOVE instruction; the first word contains
the address of the destination register."

*Grading.* "At IR2 time" is graded as tightly as sampling allows: no sample
read before the IR2 read shows the new value, which is strict by causality,
and every sample stored more than M after it does. "Directly from RAM" is
graded by (ii) and (iii): the value follows the RAM word at each execution,
not a copy of an earlier one. Every MOVE execution in the capture counts.

**5. Preconditions.** G1-G6, P1-p1, and:

| Id | Precondition | Contrasting stimulus | Predicted result |
|---|---|---|---|
| P2-p1 | The CPU write falls strictly between two IR2 reads of b_0's MOVE, and at least one execution precedes it and at least one follows it within the capture | The CPU writes $AAAA to $0E000E in step 3, before the Copper starts | No execution precedes it, so P2-p1 goes red |

**6. Contrasting case.** The CPU write is omitted. Prediction: every
execution reads $8001 and the b_0 interval shows $0001 in every field. The
main run's expectation ($2AAA after the write) fails.

**7. Reference frames.** Execution identity comes from I1 pairs. The before
and after split is the port order of the CPU write against r2(e). Sample
timing follows I2's read-before-store rule. M is in memory cycles (I4).

### P3. A MOVE after a WAIT is performed once the WAIT is satisfied, and not before

**1. Proposition.** A MOVE placed after a WAIT is performed only after the
beam has reached the WAIT's position, and then it is performed. A MOVE placed
after a WAIT that can never be satisfied is not performed.

Claims: `ch2-about-the-copper.c18.s2`, `ch2-about-the-copper.c13.s2` (p.19).

**2. Stimulus.** Run P3 (3 fields captured, monitor loop running). List L_3 at
$0E2000:

```
$0E2000  $009A,$7FFF      MOVE INTENA: clear all
$0E2004  $6401,$FF00      WAIT line $64 (100), horizontal masked (p.23 form)
$0E2008  $009A,$8004      MOVE INTENA: set bit 2
$0E200C  $FFFF,$FFFE      park
```

**3. Observation.** The I2 samples of each field, restricted to *s* >
t2(clear MOVE) + M and to the field of that execution. The page says the MOVE
happens "when the WAIT condition has been satisfied". The test knows the
condition holds from the beam reading: the WAIT is satisfied once the beam
line is >= $64 (p.22: "wait until the video beam counters are equal to (or
greater than) the coordinates", horizontal masked). Let t_m be the time of the
MOVE's IR1 read.

**4. Expected value.**

- (i) Every sample whose beam reading is below ($64, H=0) shows INTENAR bit 2
  = 0. Its INTENAR was read before its beam, and so before line $64.
- (ii) Every sample whose beam reading is >= ($66, 0) shows bit 2 = 1. The
  two-line allowance covers the WAIT's wake-up and the MOVE (p.20: the WAIT
  "requires three memory cycles"; the MOVE requires "four memory cycle
  times") as well as the gap between a sample's INTENAR read and its beam
  read. That gap is below M.
- (iii) Every sample with *s* > t_m, in the same field, reads line V >= $64.
- (iv) The MOVE at $0E2008 is fetched exactly once per field.

Sources: p.19: "When the WAIT condition has been satisfied, the Copper steals
memory cycles from either the blitter or the 680x0 to move the specified data
into the selected special-purpose register." p.19: "its ability to WAIT for a
specific video beam position, then MOVE data into a system register." p.22
(quoted above).

**5. Preconditions.** G1-G6, and:

| Id | Precondition | Contrasting stimulus | Predicted result |
|---|---|---|---|
| P3-p1 | The Copper really waited: at least one sample with *s* > t2(WAIT) reads a line below $64 | The WAIT is `$0001,$FF00` (line 0, satisfied at once) | No sample after the WAIT fetch reads a line below 0, so P3-p1 goes red |
| P3-p2 | The clearing MOVE is fetched before the WAIT in every field, so bit 2 is 0 when the waiting begins | The clearing MOVE is removed (the list starts with the WAIT) | No clearing fetch occurs, so P3-p2 goes red |

**6. Contrasting cases.**

- C1: the WAIT is `$A001,$FF00` (line 160). Prediction: bit 2 becomes 1 only
  from line $A0 on, and (ii) of the main run fails for lines $66-$9F.
- C2: the WAIT is replaced by a park `$FFFF,$FFFE` (p.23: "This event will
  never occur"). Prediction: the MOVE at $0E2008 is never fetched, so (iv)
  fails, and bit 2 stays 0 all field, so (ii) fails.

**7. Reference frames.** The beam line comes from I2 (p.285 bit layout), with
field boundaries at the wraps. G5 checks the anchor: 227 memory cycles per
line in PAL.

### P5. One long-word write to COPxLCH loads the whole list address; the lower-addressed register holds the high bits

**1. Proposition.** A CPU write to the pair COP1LCH/COP1LCL ($080/$082) or
COP2LCH/COP2LCL ($084/$086) loads the list address. The register at the lower
address receives the high bits (A20-A16 with ECS; A18-A16 on every page) and
the one at the higher address receives bits A15-A1. A single long-word write
to the H register loads both. After a word write to the matching strobe
(COPJMP1 $088 or COPJMP2 $08A), the Copper's next instruction fetch is at that
address. These registers accept CPU writes (the *write* half of
"write-only").

Claims: `COP2-location-registers.c6`, `COP2-location-registers.c9` (p.25, in
part, section 2); `ch2-location-registers.c3.s2`, `ch2-location-registers.c5.s2`
(p.25, in part); `ch2-location-registers.c11`, `COP2-location-registers.c13`
(p.25); `ch2-appa-location-registers.c2.s2, c7.s2, c11.s2, c16.s2` (p.273);
`ch2-appb-table.c16.s2, c22.s2, c26.s2, c32.s2` (p.290);
`ch2-appc-ecs.c3.s2, c8.s2` (p.309); `ch2-appb-legend.c6.s2` (p.287). All of
the location-register claims are used in part, as section 2 says.

**2. Stimulus.** Run P5 (no monitor loop; the CPU paces steps by polling
VHPOSR). At each of the 40 targets of P1 (S_L1, S_L0, S_H1, S_H0) there is a

- *Phase 1* (COP1): for each target T, at a beam line between $28 and $FA

- *Phase 2* (COP2): the CPU first executes `MOVE.L #$000E8000,$DFF080`

This follows p.25 ("you write the 18-bit address by moving one long word to
the register whose name ends in "H"") and p.139, which gives the same long
write for AUDxLCH.

**3. Observation.** I1 instruction fetches between marker M_T and the next
step's marker.

**4. Expected value.** For each step, the first Copper instruction fetch after
M_T is at T, and all Copper reads until the next marker belong to the park at
T. In phase 3 the fetch is at $0E9010. T is formed as in P1-B:
((H AND $1F) << 16) OR L, with H = T >> 16 written to the lower register
address.

Sources: p.25: "The register with the lower address always has a name ending
in "H" and contains the most significant data, or high 3 bits of the address.
The register with the higher address has a name ending in "L" and contains the
least significant data, or low 15 bits of the address." ... "This is because
when you write long words with the 680x0, the most significant word goes in
the lower addressed word." ... "When a jump address strobe is written, the
corresponding location register is loaded into the Copper program counter."
p.276: "They are transferred to the program counter whenever strobe addresses

*Quantifiers:* each address bit A1-A20 is exercised as a walking one and as a
walking zero (the sets of P1, with the background for bits 1-4 noted there).
The verdict is reported as bits A15-A1, A18-A16, and A20-A19 (ECS pages only,
3.2). "Always" (every register pair) is graded only for COP1LC,
COP2LC and, in P7, AUD0LC. "Only" in write-only is not graded (section 2).

**5. Preconditions.** G1-G4 (G3 with L = D), and:

| Id | Precondition | Contrasting stimulus | Predicted result |
|---|---|---|---|
| P5-p1 | Every marker's beam reading lies between lines $28 and $FA, so no vertical-blank restart falls inside a step | One phase-2 step is performed at line 5 | The marker reads line 5 and P5-p1 goes red. A fetch at D may precede the landing, because p.25 has COP1LC used at vertical blank. |
| P5-p2 | Before each marker the Copper is parked: no Copper read occurs between the previous landing's park fetch and M_T | The park at $0C0020 is replaced by `$F001,$FF00` (WAIT line $F0) followed by a park | A Copper read at line $F0 falls into a later step and P5-p2 goes red |

**6. Contrasting cases.**

- C1 (which register holds the high part): phase 3 with the two words

- C3 (strobe selects the register): in one phase-2 step, COPJMP1 is written

**7. Reference frame.** Markers carry beam readings (I3). Fetches follow I1.

### P6. The Copper restarts from COP1LC once per field, during vertical blanking, without a strobe

**1. Proposition.** Without any strobe write, the Copper program counter is
reloaded from COP1LC once in every field, within vertical blanking.

Claim: `appB-note.c9` (p.288: "Used to automatically restart pointers, such as
the Copper program counter (during vertical blank)").

**2. Stimulus.** Run P6 (5 fields captured, monitor loop running), in PAL and
in NTSC. Parks L6a ($0E3000), L6b ($0E3100) and L6c ($0E3200). Before step 5
the CPU executes `MOVE.L #$000E3200,$DFF084` (COP2LC = L6c). The frame then
starts the Copper with L = L6a. The program never writes a strobe after
step 5.

**3. Observation.** I1 instruction fetches, and the I2 samples around each
fetch. A *restart* is the first instruction fetch in a field. The page says
"during vertical blank", and the test knows vertical blanking holds from the
beam line: line 0 up to line $1D (PAL) or $15 (NTSC), the widest reading of
the pages that still agrees on the start (3.3). The first field (the one with
the start strobe) is excluded.

**4. Expected value.**

- (i) In every field there is exactly one instruction fetch, at the value of
  COP1LC (L6a), and no other Copper read.
- (ii) The restart's IR1 read time t_r lies after the time *s* of the last
  sample of the previous field, and before the time *s* of the first sample
  of its own field that reads line $1E or later (PAL) or $16 or later (NTSC).
  Because a sample's beam is read shortly after its *s*, the bounds carry a
  tolerance of less than M at each end.
- (iii) No fetch occurs at L6c, the COP2LC value.

The measured restart line is reported.

Sources: p.288 (claim); p.30: "if the contents of COP1LC are not changed,
every time vertical blanking occurs the Copper will restart at the same
location"; p.25 and p.276 (3.3); p.219 and p.79 for the extent of vertical
blanking.

*Quantifier ("automatically", each field):* every field in the capture, in
both video standards. p.25's "no matter what the Copper is doing" is tested
only with the Copper parked and is not graded otherwise.

**5. Preconditions.** G1-G6, and:

| Id | Precondition | Contrasting stimulus | Predicted result |
|---|---|---|---|
| P6-p1 | Between restarts the Copper is parked: no Copper read between one restart's pair and the next | L6a is `$6401,$FF00` followed by a park | Reads at line $64 occur in mid-field, P6-p1 red |
| P6-p2 | At least four wraps fall in the capture | The capture is 2 fields long | P6-p2 red |

**6. Contrasting case.** In field 3 the CPU executes
`MOVE.L #$000E3100,$DFF080` (COP1LC = L6b) once, at a beam line between $64
and $C8, bracketed by markers, with no strobe. Prediction (p.30, and p.32:
"Before the next vertical blanking time, however, the COP1LC registers must
be repointed ... The value in the COP1LC location registers will be restored
to the Copper's program counter at the start of the vertical blanking
period"): no fetch at L6b before the next wrap, the restarts of fields 4 and 5
at L6b, and none at L6a. The main run's expectation (L6a in every field)
fails.

**7. Reference frames.** Wraps and lines come from I2 and are checked by G5.
Restart identity comes from I1.

### P7. The audio pointer restarts from AUD0LC whenever the length count finishes

**1. Proposition.** With audio channel 0 running from AUD0LC = A with AUD0LEN
= N, each time the channel has fetched N words the next fetch is again at the
address held in AUD0LC. This holds at every block end.

Claims: `appB-note.c11`, `appB-note.c9` (p.288: "and the audio sample counter
(whenever the audio length count is finished)").

**2. Stimulus.** Run P7 (no Copper; 1 field captured after the enable). The
buffers hold distinct words: A = $0E4000 holds $1101, $1102, $1103, $1104 and
B = $0E4100 holds $2201, $2202, $2203, $2204. The 4 guard words after each
buffer hold $0000. In the order of p.145 ("3. Set the location registers ...
4. Set the length register ... 5. Set the volume ... 6. Set the period ... 7.
Start the audio DMA"):

1. `MOVE.L #$000E4000,$DFF0A0` (AUD0LCH; p.139: "writing a long word into
   AUDxLCH moves the audio data address into both locations")
2. AUD0LEN ($DFF0A4) ← 4
3. AUD0VOL ($DFF0A8) ← 0
4. AUD0PER ($DFF0A6) ← 500 (at least the minimum of 124 NTSC or 123 PAL,
   p.140)
5. marker
6. DMACON ← $8201 (SET/CLR, DMAEN, AUD0EN; p.144)
7. read DMACONR and store it at $0E7108

The CPU then idles in its own code region.

**3. Observation.** Channel-0 fetches: reads in the audio regions. A *block*
is a maximal run of consecutive channel-0 fetches whose addresses step by +2.
The page says "whenever the audio length count is finished". The test knows
the count has finished when the block holds N = 4 fetches. The first block
after the enable is excluded (3.6).

**4. Expected value.**

- (i) Every block after the first is exactly LC, LC+2, LC+4, LC+6, where LC is
  the value in AUD0LC.
- (ii) Every fetch at LC+6 is followed, as the next channel-0 fetch, by a
  fetch at LC.
- (iii) No read ever occurs at a guard word.

Sources: p.139: "Each time the system retrieves the last audio word from the
data area, it uses the contents of these location registers to again find the
start of the data." p.145: "the number of data words to be retrieved before
starting at the address currently in AUDxLC". p.147: "Each time the length
counter reaches zero, both the location and length registers are reloaded
with the same values to continue the audio output."

*Quantifier "whenever":* every block end in the capture.

**5. Preconditions.**

| Id | Precondition | Contrasting stimulus | Predicted result |
|---|---|---|---|
| P7-p1 | Audio fetches are identifiable: a baseline with DMACON $8200 shows no read in the audio regions | The baseline program also reads $0E4000 once | P7-p1 red |
| P7-p2 | DMACONR at $0E7108 has bits 9 and 0 set and bits 3-1 clear (p.278), so only channel 0 runs | DMACON is written $8203, with AUD1LC also pointing at A | Bit 1 reads 1 and P7-p2 goes red |
| P7-p3 | The first channel-0 fetch after the marker lies in A's buffer (p.148: the location "will be used as a pointer showing current data word to fetch") | AUD0LC is set to B instead | The first fetch is in B's buffer and P7-p3 goes red (for the main-run expectation) |
| P7-p4 | At least 10 block ends after the first block fall in the capture. With a period of 500 per sample, a word lasts 1000 memory cycles (about 4.4 lines), so a PAL field holds about 17 blocks of 4 words. | AUD0LEN = 64 | About one block per field, so P7-p4 goes red |

**6. Contrasting case.** At a time inside the fourth block, after its second
fetch and before its last (bracketed by markers, which the checker verifies
against the fetch times), the CPU executes `MOVE.L #$000E4100,$DFF0A0`
(AUD0LC = B). Prediction (p.147: "Once the original registers have been read
by the DMA channel, you can change their values without disturbing the
operation you started"; p.148): the fourth block completes at A+6, the next
fetch is at B, and every later block is B, B+2, B+4, B+6. The main run's
expectation (return to A) fails.

**7. Reference frame.** Block boundaries are defined by the fetch address
sequence itself. Markers bracket the CPU's register write (I3).

## 7. What the build added

This package builds P3, P4 and P1's instrument A (P1-A: INTENA read back
through INTENAR) only. P1's instrument B (COP2LC, the 40-target address
chain), P2, P5, P6 and P7 are not built.

**Programs.** `ch2move.i` holds the custom-register offsets nanomig.i does
not define and the common frame macro (section 4.3, steps 1-2), shared by
every program below.

- `prog_p4.s`, with `prog_p4_mut_extra.s`, `prog_p4_mut_clearlate.s` and
  `prog_p4_mut_swap.s`: P4.
- `prog_p3.s`, with `prog_p3_nocopen.s`, `prog_p3_nocopen_mut.s`,
  `prog_p3_mut_wait0.s`, `prog_p3_mut_noclear.s`, `prog_p3_c1.s`,
  `prog_p3_c2.s`, `prog_p3_g3.s`, `prog_p3_g4.s` and `prog_p3_g6.s`: P3,
  and the first demonstration of the shared instruments G1-G6 (section
  4.5). P1-A below reuses the same, unchanged instrument code and
  restates every one of G1-G6 on its own two captures; it does not repeat
  G1/G4/G5's own dedicated mutations, since those would exercise the same
  measuring apparatus P3 already demonstrated, not a further
  proposition-specific claim.
- `prog_p1a.s`, with `prog_p1a_clear.s`, `prog_p1a_mut_p1p1.s`,
  `prog_p1a_mut_p1p2.s`, `prog_p1a_c1.s`, `prog_p1a_c2.s`,

  `p1a_list_set_c1.i`, `p1a_list_set_c2.i` and `p1a_list_clear_c1.i`: P1's
  instrument A.

**Measured values.** I4's own ratio (one memory cycle to `clk_sys`
cycles) is asserted, not assumed: every line's own first-to-last-sample
ratio is measured and required to round to the same integer over the
whole capture (4.4). It is 8 on both cores, in every capture this package
runs, with every line agreeing. G5's mean line length (4.5), over every
corrected gap in the capture, sits within 0.3 memory cycles of 227 in
every capture this package runs, fx68k and TG68K alike; no single
corrected gap in any capture reaches the 40-memory-cycle gross bound.
Every capture in this package runs the monitor loop for a fixed 30000
iterations, comfortably longer than
any proposition's own field count; 13 to 15 fields were observed per
run, on both cores.

**Mutations.** Every `NMH_MUTATE` value the test file's header names ran
on both cores. Most go red through exactly the clause(s) their header
names, with the rest of the setup unaffected. The exceptions, each for a
reason the header states: `P3-P1` (WAIT line 0) also turns `P3-i` and
`P3-iii` red, the page's own consequence of an instantly-satisfied WAIT,
not a separate fault; `P3-C2` (the WAIT replaced by a park) reaches
neither a WAIT-shaped nor a set-MOVE fetch, so `P3-fixture` goes red and
`P3-ii`/`P3-iv` are recorded, not graded; `P3-G6` (added monitor-loop
delay) also carries away I4 and G5 on TG68K, a natural consequence of
too few samples per line for either to measure anything, not a separate
fault. `G2`'s own contrast is demonstrated on the no-COPEN baseline
every run already builds for G1 (`prog_p3_nocopen.bin`), not a separate
mutation. `P3-G5` (the same program run with NTSC selected, checked with
the PAL rule) does not reach a red: the mean line length measured is
still 227.0 under NTSC selection too, both cores, so p.23's own 227/228
alternation is not reproduced at this boundary. This is recorded, not
graded, and does not weaken G5's own PAL-rule assertion, which is
graded, on every capture, against every capture's own measured ratio
(4.4) rather than an assumed one.
